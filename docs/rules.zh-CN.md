# `akio` 开发规则

[English](rules.md) | 简体中文

`akio` 的每一处改动都遵循这些规则。它们补充 [DEV-PLAN 第 5 节](DEV-PLAN.zh-CN.md) 的工程规则和各
ADR：那些规定代码如何组织和验证，这里规定数据面绝不能做什么。规则改编自
[fit 的规则](https://github.com/lesismal/fit/blob/main/docs/rules.zh-CN.md)，后者对基于事件循环库构建的
代理坚持同样的底线。

## 1. 绝不阻塞 I/O 线程

1. **I/O 线程上的任何代码都不阻塞。** handler、中间件、协议状态机和完成回调运行在拥有该连接的事件循环
   上，与这个线程的所有其他连接共用它。它们不做同步磁盘 I/O（`std::fs`、`File::open/read`、
   `metadata`），不做 DNS 解析（`to_socket_addrs`），不 `thread::sleep`，不等待 channel、条件变量、
   join handle 或 future，不做阻塞 `connect`，也不持有其他线程可能长时间持有的锁。慢回调检测
   （`Config::slow_callback_threshold`，默认 100 ms）会报告漏网之鱼。
2. **只能阻塞的工作交给逻辑线程池**：用 `Conn::spawn_blocking`（或由线程池完成的 detach 响应、
   `Context::detach_to_pool`，或各协议的 `handlers_on_logical_pool` 开关，ADR-094），
   以完成回调的形式回到事件循环。线程池有界（满时返回 `Overloaded`），往里排队工作的功能必须处理这个
   错误。线程池与事件循环之间的等待只有一个方向：线程池任务从不等待事件循环，二者不会互相死锁。
   能避免时，线程池任务也不等待同一个线程池中的其他任务（投递子任务后在其 channel 或 join 上阻塞）：
   一旦所有线程都被这样的等待者占住，子任务就留在队列里没有线程执行，这些请求永久卡住，新请求则被拒绝。
   线程池任务本来就可以阻塞，所以子工作直接内联执行；下一阶段从回到事件循环的完成回调开始；需要并行再
   汇总的工作使用自己的独立线程池。必须等待同一线程池可能要产出的结果时（调用同一 engine 上 handler
   也在线程池上运行的服务），线程池任务把这次等待包在 `akio::blocking` 里：线程池会启动一个线程顶替
   等待者，等待结束后这个线程随即退出。各库的阻塞客户端（`ResponseFuture::wait`、`CallFuture::wait`、
   gRPC `unary`、各 `*_blocking` 调用）已经这样做。顶替线程的数量受 `PoolConfig::max_blocked_threads`
   限制；超过后工作只能等待（由 `PoolStats::blocked_at_ceiling` 计数）。线程池任务对其他服务的阻塞调用（HTTP 或 gRPC 客户端）都要带超时，
   因为每次等待都占着一个线程池线程。只需要进入某个连接的事件循环的代码（发起客户端请求、触发超时）
   使用 `Conn::run_on_loop`，绝不投递空的 `spawn_blocking`，这样它不需要任何线程池线程。
   线程池满时只拒绝新工作。已接受工作的下一步（进行中的响应的下一段、已打开调用的下一条消息、
   已下载完整的 piece）走 `resume`（`Pool::resume`、`ConnInner::resume`、`Executor::resume`），
   队列满也不拒绝；它的所有者同一时刻只保留一步在排队或执行，这条车道因此有界。被拒绝的投递绝不
   通过定时器稍后重试：定时器只用于本身与时间有关的逻辑（超时、空闲回收、周期任务）。
3. **必须调用阻塞 API 的库代码**（tracker announce 解析主机名、缓存未命中时读取文件）在线程池或它自己
   的专用线程上调用，绝不在恰好触发它的事件循环上调用。只有纯内存的快速路径留在事件循环上。

## 2. 消息体流式处理且有界

4. **消息体随到随处理**（`BodyMode::Stream`、`on_body`、帧回调），分段转发。只有确实需要完整消息的
   功能才缓冲它，并且总有上限；超过上限时返回 413 / `ResourceExhausted` / 关闭码 1009，或退回流式处理。
5. **交给回调的数据只在那一次调用内有效**；要在调用之后保留就复制，最好复制到池化的缓冲区（`akio-buf`）。
6. **限制在付出展开代价之前就计算对端能控制的量**：压缩输入和它解压后的输出都受限，未完成的消息和分片
   与完整消息一样受限，整个连接的总和与每个流一样受限。

## 3. 背压联动，没有无界的东西

7. **任何队列或缓冲区都不能无限增长**：每连接发送队列（`max_queued_bytes`）、多路复用协议中每个流和
   每个连接的待发字节、有序（流水线）响应、慢订阅者的扇出队列、以对端输入为键的表（UDP 对端、会话、
   流、swarm、缓存）。每张表都有上限和淘汰规则。
8. **背压联动**：一侧的待发字节超过水位线时暂停另一侧的读取（`hold_reads`），排空后恢复（`on_drain`）。
   中继和隧道（SOCKS、CONNECT、WebSocket 和 gRPC 代理、媒体扇出、TURN）双向施加背压。

## 4. 超时与上限

9. **与外部的每一次交互都有超时**：连接、首字节 / 请求头、空闲和总时长。一次一个字节的涓流不能让
   收了一半的请求头一直存活（slowloris）。
10. **每种资源都有上限，每个上限都有安全的默认值**：连接、流、会话、对端、头大小、消息体大小、消息大小、
    解压后大小、并发、单位时间内的重置次数。一个什么都没设置的配置仍然有界；"不限"是显式的选择，
    绝不是默认值。[ADR-009](adr/009-safe-defaults.zh-CN.md) 列出了引擎的默认值。

## 5. 热路径

11. **能在构建配置时完成的事不留到请求时做。** 路由、中间件链、固定的头值（CORS、`Allow`、`Server`）、
    压缩选择和查找表只构建一次。请求只读取不可变的结构。
12. **每个请求或每条消息：不用全局锁，尽量少分配。** 共享计数器按线程或分片；不在每个请求上增减所有
    线程共享的引用计数；缓冲区复用或池化；能在构建时格式化的内容不在请求时格式化。

## 6. 验证

13. **每个数据面功能都有测试**：慢对端、大消息体、中途断开的连接，以及它引入的上限（略低于、等于和
    超过），覆盖该功能运行的每个后端。
14. **影响吞吐或内存的改动要在安静的基准主机上做前后对比**，规模按规则 16 确定，数字写进提交或报告。
15. **新增依赖要附 ADR**（ADR-005：库没有必需的第三方依赖）。

## 7. 验证与改动相称

每项检查都要花等待时间；每个改动只做它这一类所需的检查，不多做。

16. **按类型做基准测试。**

    | 改动 | 基准测试 |
    | --- | --- |
    | 文档、测试、配置、控制面 | 无 |
    | 热路径之外的数据面（上限、超时、错误路径） | 无，或该 crate 的微基准 |
    | 热路径（读写路径、解析器、路由、加密内核） | 在安静主机上（`quiet.sh`）同一轮交替进行的前后 A/B |
    | 发布或一轮完整测评 | 完整的测评框架（`tools/bench`）并更新 `docs/BENCHMARKS.md` |

    功能开发任务中，这一列留给单独的压测任务（规则 20）。

17. **压测和基准测试在 Linux 的基准主机上运行。** 不使用 macOS、Docker Desktop 或有负载主机上的数字；
    主机有外部负载时只报告同一轮 A/B 的比值。同一时间只有一个会话使用基准主机。
18. **按影响范围测试。** 开发过程中运行改动涉及的 crate 及依赖它们的 crate 的测试；完整的工作区测试
    （macOS、Docker 中 Linux arm64 的 epoll 和 io_uring、x86_64 Linux 原生）在合并或推送前跑一次。同时
    最多两个会话运行完整测试。

## 8. 清理

19. **每次开发、测试和基准运行结束后都要清理自己留下的东西，释放占用的空间。** 工作完成后（一个功能、一次修复、一次
    测试或基准运行、一次复现），清除它在本机和基准主机上留下的东西：为它产生的构建输出（副本和 worktree 的
    `target/` 目录、测试二进制）、源码树副本和 git worktree、它创建的容器、镜像和卷，以及不再需要的日志和临时文件。
    有意保留的缓存（测评框架共用的 target 目录、固定版本的镜像）保留，但增长后要修剪。基准主机的磁盘由所有会话共用：
    大规模构建前先查看剩余空间（`df -h /`），离开时不要比来时更满；磁盘写满会让所有人的构建和运行停下。

## 9. 功能开发与压测

20. **功能开发任务只跑基础的 CI 测试，不做压测和基准测试。** 开发功能或修复 bug 的任务只跑 CI 所跑的内容：它涉及的
    crate 的 `cargo test`（推送前再按规则 18 跑一次完整工作区测试）、fmt 和 clippy。不做压测、基准测试、A/B 对比、
    性能剖析、完整测评框架运行，也不做压力和长时间稳定性测试（大量重复次数、长时间带负载运行），本机和基准主机上都
    不做。基准主机的时间留给维护者另外单独进行的压测任务（HTTPArena 等）；功能任务占用主机既浪费机器时间，也会干扰
    或拖延这些压测。其他规则要求测量的，功能任务留给这样的压测任务，并在报告中写明应当测什么。只有用户在该任务中明
    确要求时，功能任务才跑基准测试。

    功能需要基准测试（规则 16）的功能开发任务，要在 [DEV-PLAN 第 4 节](DEV-PLAN.zh-CN.md)的基准测试状态表中添加或保留
    它的行，标为未测、未优化，并在其中写明应当测什么；压测任务测过、优化过之后更新该行。未测或未优化的行就是待办项。

## 10. 卡死的运行不能无人察觉

21. **测试卡死只能浪费几分钟，不能浪费几个小时。** 让测试死锁的 bug 必须让运行很快、明显地失败，绝不能让它一直等下去：
    - **每个测试二进制都有时间上限。** 完整工作区测试和其他长时间的测试运行，通过 cargo runner
      [`tools/test-timeout.sh`](../tools/test-timeout.sh) 启动每个测试二进制（`CARGO_TARGET_<TRIPLE>_RUNNER`，例如
      `CARGO_TARGET_X86_64_UNKNOWN_LINUX_GNU_RUNNER=$PWD/tools/test-timeout.sh`）。运行超过
      `AKIO_TEST_BINARY_TIMEOUT` 秒（默认 900；最慢的二进制约 5 分钟）仍未结束的二进制，会输出一行 `HANG:` 和它的
      线程（测试框架用测试名给测试线程命名，所以能看出卡住的是哪个测试），然后被杀掉，运行继续下一个二进制。
    - **`HANG:` 和其他失败一样对待**：要报告，并用 `timeout` 单独重跑该测试几次，区分偶发卡死和改动引入的死锁。
    - **等待长时间运行的人要盯进度，而不只是等结束。** 监视程序检查日志是否持续增长，15 分钟没有增长就报告；
      然后查看正在运行的进程（`ps`、测试二进制在 `/proc/<pid>/task/*/comm` 和 `wchan` 里的线程）。只等结束标记是不够的。
    - **测试自带截止时间。** 等待 socket、channel 或条件的测试要设置读写超时、`recv_timeout` 或有上限的等待，
      让 bug 使测试失败，而不是卡死。
