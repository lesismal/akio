# 弃用流程

[English](deprecation.md)

从 1.0.0 起，受保护的 API（[api-stability.zh-CN.md](api-stability.zh-CN.md)）绝不会在没有预警的
情况下被删除或修改。需要移除某个条目时，先将其弃用，至少保留一个次版本继续可用，并且只在下一个
主版本中删除。

## 步骤

1. **先提供替代品。** 新 API 在某个次版本中加入，早于弃用或与弃用同时。没有替代品的弃用需要在
   说明中给出理由（该功能将被移除）。
2. **标记条目**，写明弃用它的版本以及替代品：

   ```rust
   #[deprecated(since = "1.4.0", note = "use `H2Client::dial` instead; removed in 2.0")]
   pub fn connect(/* ... */) { /* 转发给替代品 */ }
   ```

   - `since` 是第一个带有该属性的发布版本。
   - `note` 以可搜索的路径写出替代品，并说明计划何时移除。
   - 被弃用的条目保持原有行为；能转发给替代品时就转发。
   - 若变更不只是改名，在其文档中增加 `# Deprecated` 段落并附迁移示例。
3. **保持 workspace 无警告。** CI 拒绝警告，因此仓库内的调用者、示例、书和指南在同一次变更中改用
   替代品。必须继续使用旧条目的代码（测试被弃用的路径）用局部的 `#[allow(deprecated)]` 说明。
4. **记入 `CHANGELOG.md`**（以及 `CHANGELOG.zh-CN.md`）对应版本的 `Deprecated` 部分，并写明替代品。
   API 快照（`tools/api/public-api.sh --bless`）在同一次提交中更新。
5. **等待。** 被弃用的条目至少保留一个次版本，并且无论如何保留到下一个主版本：删除属于破坏性
   变更。
6. **在主版本中删除**，并在变更日志的 `Removed` 中列出及其迁移方式（发布说明中的迁移表把每个被
   删除的条目指向其替代品）。

## 其他情况

- **隐藏和不稳定条目**（`#[doc(hidden)]`、`fuzzing` feature、将来的 `unstable` feature）不在承诺
  范围内，可以不经弃用直接修改。代价不大时我们仍会先弃用，因为其他 workspace crate 和早期用户在
  使用它们。
- **行为变更**（默认值、上限）虽不是 API 变更，也遵循同样的精神：在次版本的变更日志中公告，合理时
  提供保留旧行为的设置，只在主版本中修改默认值，除非是为了修复缺陷或安全问题。
- **安全修复**在没有其他办法堵住漏洞时，可以在次版本或补丁版本中造成破坏；变更日志会明确说明
  （见 [SECURITY.zh-CN.md](../SECURITY.zh-CN.md)）。
- **1.0.0 之前**（包括发布候选版）API 可以不经弃用期直接修改；每次修改仍会连同迁移方式写入变更
  日志。
