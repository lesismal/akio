# 基准测试

[English](BENCHMARKS.md) | 简体中文

测量日期 2026-11-14，基于提交 `23d9c59` 之后的分支（即下文的性能与内存优化）。**请先读“局限”**：
只有一台笔记本上的虚拟机，测量期间还被其他繁忙任务共享。各轮之间的波动经常达到 ±20%，有时更大；
跨库对比表中 20% 以内的差别请视为噪声，只用来判断“是否同一量级”，不要当作排名。优化前后的对比是
另外测的（两个构建交替运行），比跨库对比表可信。

## 环境

- 一台 Docker 虚拟机（linuxkit，Linux 6.12.5，aarch64），宿主是 Apple 芯片的 Mac，**14 个 vCPU 与其他
  任务共享**：测量期间，其他 agent 的容器（fuzzer、测试套件、Autobahn 服务器）一直占用约 4–5 个
  vCPU，且没有绑核，所以也会跑到基准测试使用的 CPU 上。只走回环，没有网卡。
- 服务端绑定在 CPU 0–3，4 个 I/O 线程（tokio：4 个 worker；fib：`GOMAXPROCS` 随 4 核亲和性）。
  压测端绑定在 CPU 4–11，8 个线程。
- 每个数字是 **3 轮的中位数**，每轮 5 秒，预热 1 秒（A/B 对比：5 轮）。每一轮依次对每个服务端跑每个
  场景，每次都重新启动服务端，因此一阵噪声只会落在每个服务端的某一次上，而不是集中在某一个服务端。
  数字后的 `±` 是各轮最大值与最小值之差的一半，占中位数的百分比。
- 每次运行前脚本会采样 `/proc/stat`，若虚拟机忙碌超过 45% 则等待（最多 15 秒）；其他任务很少让它
  更空闲，所以这只能避开最严重的突发。虚拟机之外（macOS 宿主）的负载它看不到。
- 服务端（处理逻辑一致）：
  - **only-epoll / only-uring**：`crates/only/examples/bench-server.rs`（TCP/TLS/UDP echo）和
    `crates/only-http/examples/http-bench.rs`（HTTP/1.1 + h2c 的 `/plaintext`、`/json`，`/ws` 上的
    WebSocket echo），分别使用 `Backend::Epoll` / `Backend::IoUring`。
  - **tokio**：`tools/bench-ref/tokio-ref`（tokio 1，每连接一个 task，64 KiB 读缓冲；TLS 用
    tokio-rustls；WebSocket 用 tokio-tungstenite 0.28）。
  - **hyper**：`tools/bench-ref/hyper-ref`（hyper 1 + hyper-util `auto`：HTTP/1.1 与 h2c）。
  - **fib**：`tools/bench-ref/fib-ref`（Go 1.27.3，fib 默认配置；TLS 用 `fib/tls`，HTTP 用
    `fib/http`，WebSocket 用 `fib/websocket`）。
- TLS：TLS 1.3，所有服务端都用 ECDSA P-256 自签名证书（only 与 tokio 用 rustls + ring，fib 用
  crypto/tls）；客户端不校验证书。
- 压测工具：`wrk` 4.1（HTTP/1.1；流水线用 Lua 脚本一次写 16 个请求），`h2load` 1.64（HTTP/2 prior
  knowledge，64 连接 × 16 流，8 线程），以及仓库内的 `tools/echo-bench`（TCP/TLS/UDP/WebSocket 的
  闭环 echo、完整 TLS 握手速率，以及内存测试中保持连接的客户端）。
- JSON：hyper 用 serde_json，fib 用 `encoding/json`，only 在示例里用一个手写的小序列化函数（only
  不依赖 JSON 库）；三者都是每个请求现场生成响应体。

## 复现

```sh
docker build -t only-bench tools/bench          # rust:1 + wrk + h2load + perf + Go
PRIV=1 tools/bench/docker.sh 'tools/bench/build.sh && tools/bench/all.sh /tmp/t/results'
```

`docker.sh` 把仓库挂载到 `/w`，把 fib 检出目录（主 only 检出目录旁的 `../fib`，或 `$FIB_DIR`）挂载到
`/fib`，用卷保存 cargo registry、target 目录和 Go 模块，把 `nofile` 提高到 1M，并设置适合回环压测的
sysctl（临时端口 10000–65535，高于服务端端口；`tcp_tw_reuse`）。各部分也可单独运行：
`echo.sh [tcp,udp,tls,tlshs]`、`http.sh [plaintext,pipelined,json,h2,ws]`、
`mem.sh [proto:kind:conns ...]`，以及 `profile.sh <h1|pipelined|h2|ws|tcp> <server>`（perf，需要
`PRIV=1`）。可调参数（`SRV_CPUS`、`CLI_CPUS`、`THREADS`、`SECS`、`RUNS`、`KINDS`，以及用于和另一版本
二进制做 A/B 对比的 `BASE_DIR`，在表中显示为 `base-epoll` / `base-uring`）见 `tools/bench/lib.sh`；
`summarize.py` 把原始 TSV 行汇总成下面的表格。

### 每连接内存

服务端 RSS 的增量除以保持打开的连接数（`tools/bench/mem.sh`）：客户端建立连接（分散到
127.0.0.1–4，使一个客户端可以保持超过 64k 个连接），每个连接完成一次交互，然后全部保持空闲，此时读取
服务端的 `VmRSS`。单位为字节/连接，未注明时为 10,000 个连接。这些运行里 tokio 的每连接读缓冲设为
4 KiB（`TOKIO_REF_BUF`，注重内存的 tokio 服务也会这样做）；吞吐测试用的 64 KiB 大部分本来也不会被
触碰。

| 连接状态 | only-epoll | only-uring | tokio | hyper | fib |
|---|---:|---:|---:|---:|---:|
| 空闲 TCP（仅建立连接） | 600 | 603 | 4,993 | – | 428 |
| 空闲 TCP，**100,000 个连接** | 562 | 564 | 5,008 | – | 275 |
| 一次 64 B echo 之后的 TCP | 607 | 6,674 ¹ | 4,993 | – | 471 |
| 一次请求之后的 HTTP/1.1 keep-alive | 912 | 7,000 ¹ | – | 17,432 | 1,629 |
| 升级 + 一次 echo 之后的 WebSocket | 1,660 | 7,759 ¹ | 137,297 ² | – | 485 |
| 握手 + 一次 echo 之后的 TLS 1.3 | 8,526 | 14,598 ¹ | 15,086 | – | 6,661 |

¹ 并非每连接开销：io_uring 收数据用的是每个 I/O 线程 1024 × 16 KiB 的 provided-buffer 环（4 个线程共
64 MiB），预先分配，随着环的循环逐页被触碰。10,000 个连接各收一次数据时，其中大部分被触碰（此处约
60 MB），于是表现为每连接约 6 KB；这是一个固定上限，不会随连接数增长。在没有收过数据的空闲那一行里，
only-uring 真实的每连接开销与 epoll 相同。

² tokio-tungstenite 默认配置下每个连接保留较大的读写缓冲。

100k 连接测试（M1 遗留项）在所有服务端上都跑完了：only 在基线之上用约 55 MB RSS 保持了 100,000 个
空闲连接。

## 性能与内存优化

下面是做过的分析和修改，前后数据来自两个构建交替运行的 A/B 测试（`BASE_DIR`，HTTP 为 5 轮 × 5 秒，
其余为 3 轮；旧构建是 `23d9c59` 的代码，只加了基准测试示例）。

### 性能剖析（perf，`tools/bench/profile.sh`）

- **h2c**：服务端 65% 的 CPU 花在 HPACK 头部解码上：`loona-hpack` 每解码一个 Huffman 编码的字符串，
  都从头构建一次 Huffman 解码表（257 个码的嵌套哈希表）。修复后，剖析结果排在前面的是 malloc/free
  （约 25%）和内核。
- **HTTP/1.1 plaintext**：74% 在内核（回环 TCP、唤醒），26% 在用户态，其中最大的几项是内存分配
  （约 4%）、读时钟（约 4%：每个请求 5 次 `clock_gettime`）、请求解析和响应编码。
- **TCP echo**：受内核限制；用户态没有超过 1% 的项。

### 修改及效果

| 修改 | 位置 | 效果（中位数，A/B） |
|---|---|---|
| Huffman 解码改用只构建一次的表（`only_http::hpack`）；头部块先改写为原始字面量再交给 `loona-hpack`，动态表和校验仍由它负责；QPACK 也用同一个解码器 | only-http、only-h3 | h2c：**29.2 万 → 187 万请求/秒**（epoll，×6.4），28.7 万 → 182 万（uring） |
| 每个回调读一次时钟而不是三次：事件循环按批缓存“当前时间”，回调计时（慢回调检测）从上一个回调的结束时刻接着算；响应时间中间件只有安装时才读时钟 | only-epoll、only-uring、only-core、only-http | 与后三行合计：HTTP/1.1 plaintext **110 万 → 120 万**（epoll，+9%），114 万 → 119 万（uring，+4%）；JSON 114 万 → 120 万（epoll，+5%），116 万 → 119 万（uring，+3%）；16 请求流水线 376 万 → 440 万（epoll，3 轮，+17%） |
| `Headers` 把所有名字和值放在一个字符串里：每组头部两次分配，而不是每个字段两次；响应编码不再使用 `fmt`，日期头直接从每秒缓存写出而不克隆 | only-http | （含在上面） |
| 排在最前面的响应在 `fill` 时直接发送，不再构造只有一个元素的 `Vec<Part>` | only-core | （含在上面） |
| 连接表用一次乘法哈希代替 SipHash（`IdMap`） | only-core、各后端 | （含在上面） |
| 发送队列和响应槽队列把第一个元素内联保存，请求之间连接不再保留队列分配；有序响应状态在首次使用时（HTTP）才分配 | only-core | 一次 echo 之后的 TCP **739 → 607 B**（−18%）；空闲 TCP 554 → 600 B（+8%，内联头元素的代价），100k 空闲 533 → 562 B |
| HTTP 会话：WebSocket、HTTP/2 和请求体状态改为 Box（会话结构 736 → 200 字节） | only-http | HTTP keep-alive **1,624 → 912 B**（−44%）；WebSocket 2,085 → 1,660 B（−20%） |

TCP echo 吞吐在噪声范围内没有变化（64 B × 64：51.1 万 → 51.7 万；64 B × 1024：101 万 → 101 万）。
TLS 内存没有变化（每连接 8.5 KB，主要是 rustls 自身的缓冲）。

合并之后的 `main`（chaos 修复、lint、fuzzing）后，用同样的方法与合并前的构建做 A/B：HTTP/1.1
plaintext 没有变化（111 万对 112 万），内存没有变化（每连接相差 10 字节以内），但 h2c 慢了 9%
（182 万 → 167 万）：h2 会话现在在释放锁之后才丢弃已结束的流，而为此使用的 `Vec` 每结束一个流都要重新
分配。改为复用每线程一个的备用缓冲后，h2c 回到与合并前构建持平（宿主较忙时测得 139 万对 141 万）。

### 新增：写超时

`Config::write_timeout`（默认关闭）：连接有待发送数据、却在这段时间内没有任何写入进展时，以
`ErrorKind::TimedOut` 关闭（计入 `write_timeouts`）。已有的 `idle_timeout` 就是读超时（只有收到数据才算
活动）。两种后端都支持；检查只在有待发送数据时挂在空闲超时的时间轮上，跟得上的连接没有额外开销。

## 编解码微基准（自研 vs 被替换的 crate）

`cargo run --release --manifest-path tools/codec-bench/Cargo.toml [http1|hpack|regex]`，这是一个单独的
workspace，httparse、loona-hpack 与 regex 因此不进入库的依赖。Apple M 系列（aarch64，httparse 在此使用
NEON），取 5 轮中最好的一轮，单位为每次操作的纳秒数：

| 操作 | only | 被替换的 crate |
|---|---|---|
| HTTP/1 请求头，1 个头部 | 52 | httparse 50 |
| HTTP/1 请求头，类浏览器，11 个头部 | 192–216 | httparse 179–187 |
| HTTP/1 响应头，7 个头部 | 131–146 | httparse 150–154 |
| 同一类浏览器请求按 16 字节分次到达（增量续解析 vs 从头重解析） | 1 694–1 801 | httparse 4 597–4 767 |
| HPACK 解码，首个请求头部块，Huffman | 1 759 | loona-hpack 132 435 |
| HPACK 解码，首个请求头部块，原始字面量 | 764 | loona-hpack 902 |
| HPACK 解码，全部为索引的请求头部块 | 398 | loona-hpack 410 |
| HPACK 编码响应，动态表已预热 | 75 | loona-hpack 304 |
| HPACK 编码响应，全新动态表（only 做 Huffman 编码，loona 不做） | 368 | loona-hpack 299 |
| 路由正则 `[0-9]+` 匹配 `1234567` | 5.8 | regex 12.6 |
| 路由正则 `\d{4}-\d{2}-\d{2}` | 10.7 | regex 13.6 |
| 路由正则 `[a-z0-9_-]{3,16}` 匹配 14 个字符 | 16.0 | regex 15.8 |
| 编译 `\d{4}-\d{2}-\d{2}` | 2 652 | regex 127 213 |

头部解析器在安全代码中每次扫描 8 字节（不使用 SIMD intrinsics），对完整头部与 httparse 相差约 10% 以内；
分次到达的头部因为只检查新到的行，开销约为原来的 1/2.7。（此前 only-http 的 HTTP/2 路径已经自己解码 Huffman
字符串、再把原始字面量交给 loona-hpack，因此相对上一版本的 h2c 提升要比 Huffman 那几行显示的小。）

## Deflate（only-deflate vs flate2 / zlib-rs）

`cargo run --release -p only-deflate --example bench [FILE...]` 与 `--example pmd_echo`，于
2026-11-15 在一台安静的 x86-64 主机上测量（AMD Ryzen 7 7800X3D，Ubuntu 24.04，Rust 1.100，其他服务
已停止，用 `taskset` 绑定到单核），取 3 轮（每轮至少 200 ms）中的最好值。“之前”为第 A 波的匹配器
（zlib 的贪心/惰性匹配，3 字节哈希），“之后”为本次性能优化（4 字节哈希，zlib-ng 的
quick/fast/medium/slow 策略与级别表，每次比较 8 字节，级别 9 使用 zlib-ng 的跳链搜索；解码器快速
路径使用 64 位补充比特与分块复制匹配）。语料：生成的类英文文本（4 MB）、JSON 行（4 MB）、随机字节
（1 MB）、本仓库的 Rust 源码（4.2 MB）与 glibc 的 `libc.so.6`（2.1 MB）。解压测的是同级别 zlib-rs

## 用户态 TCP/IP 协议栈（only-dpdk）：自研 vs smoltcp

`cargo run --release -p only-dpdk --example stack-bench`（只用公开 API，同一文件可在两个版本上运行）：
两个 engine 通过进程内内存链路相连，macOS（Apple silicon，14 核）。主机同时在跑其他重负载任务
（load average 20-80），因此每个版本交替运行 5 次，表中为中位数；单次结果的波动可达 10 倍。

| | smoltcp 0.12（之前） | 自研协议栈（之后） |
|---|---:|---:|
| TCP echo，单连接，64 KiB 缓冲区 | 75 MB/s | 492 MB/s |
| TCP echo，单连接，1 MiB 缓冲区 | 105 MB/s | 1179 MB/s |
| 顺序建连（拨号、1 次请求/响应、关闭） | 2216/s | 24197/s |
| 新连接首个响应的中位耗时 | 152 µs | 36 µs |
| 100 条并发连接：全部建立 | 8.7 ms | 0.8 ms |
| 100 条并发连接：每秒请求/响应 | 155 k | 494 k |
| 1000 条并发连接：全部建立 | 14.1 ms | 10.2 ms |
| 1000 条并发连接：每秒请求/响应 | 127 k | 662 k |
| UDP 请求/响应（同时只有一个在途） | 3.2 k/s | 14.1 k/s |

部分提升来自 I/O 循环而不是协议代码：内存链路发送后会唤醒对端线程（之前空闲的对端每次交互最多可能
睡 1 ms）。不带这一唤醒的自研协议栈单次运行结果为 39 / 209 MB/s、779 连接/s、759 次 UDP 往返/s，可见
每次交互的时延主要被睡眠占据，而大块传输和多连接的数字已经来自协议栈本身（按批合并 ACK、不再每轮扫描
所有连接、定时器堆）。在 Docker 中以 Linux 内核为对端（veth 上的 AF_PACKET，`tests/kernel_peer.rs`，
release 构建）：20 ms RTT 下 4 MiB 窗口的 32 MiB echo 约为每方向 70 MB/s，500 条并发连接各 echo
32 KiB 约用 0.3 s；双向 `netem` 2% 丢包、2 ms 时延、10% 乱序时 8 MiB echo 约为 1.6 MB/s，且内核的
SACK 计数器有变化。smoltcp 版本没有 SACK 与拥塞控制，在这种链路上无从对比。

## 结论

- **TCP echo**：64 连接时 only 与 tokio、fib 持平，256 连接起领先两者，1024 连接时领先 1.3–2 倍。
  小消息时 io_uring 与 epoll 持平，16 KiB 消息时落后于 epoll；原因没有调查。
- **HTTP/1.1**：不用流水线时是 hyper 和 fib 的 1.25–1.6 倍。16 请求流水线时是 hyper 的 2.3 倍，但落后
  fib（约 0.8 倍）；原因没有调查。
- **HTTP/2**：修复 HPACK 后是 hyper 的 2 倍（之前是 0.4 倍），仍落后 fib（约 0.55 倍）；下一步的开销
  在 h2 会话里每个请求的内存分配。
- **WebSocket**：两种消息大小都领先 tokio-tungstenite 和 fib。
- **内存**：一个空闲的 only 连接约 0.6 KB，是 4 KiB 缓冲的 tokio 的 1/8，是 fib 的 1.4–2 倍。HTTP
  keep-alive 连接现在低于 fib（0.9 对 1.6 KB），远低于 hyper（17 KB）。WebSocket 连接是 fib 的 3.4 倍
  （fib 对升级后的连接保存的状态更少），TLS 连接是 fib 的 1.3 倍（rustls 缓冲）。

## 局限

- 一台笔记本级 Mac 上的共享虚拟机，测量期间其他任务一直在运行。`±` 列就是真实的误差范围：有些格子在
  不同轮次之间变化了 30–50%。绝对数值没有意义；比例只有参考价值，而且只有大的比例才有意义。
- 只走回环：没有网卡，没有真实网络延迟，客户端和服务端争用同一份内存带宽和内核锁。
- 有些格子受限于客户端（TLS 握手、1024 连接的 echo），这些数字只是服务端的下限。
- fib 和参考服务端都没有调优；fib 的 16 KiB echo 数字（只有其他的五分之一）没有调查。
- 未测量：延迟分位数、对比 quic-go 的 QUIC/HTTP/3（可选项，未做）、持续负载下的内存（只测了一次交互
  之后）、monoio。
