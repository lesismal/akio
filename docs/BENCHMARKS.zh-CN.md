# 基准测试

[English](BENCHMARKS.md) | 简体中文

2026-11-15 在一台安静的物理机上、基于同一个提交（`10070cff`，即各项自研替换和分领域性能优化之后：
密码学 CPU 加速、deflate、QUIC 节拍器、TLS 记录路径、h2 与 HTTP/1）跑的一次完整测试。下面所有表格
都来自这一次测试；此前各领域的优化前后数字压缩在[历史](#历史)一节。

## 主机与方法

- **主机**：AMD Ryzen 7 7800X3D（Zen 4，8 核 16 线程，最高 5.05 GHz，AES-NI、SHA-NI、PCLMULQDQ、
  VAES、AVX-512），61 GB 内存，Ubuntu 24.04，Linux 7.0.0-42，x86-64，非虚拟机。
- **工具链**：Rust 1.100.0（工作区的 release 配置），fib-ref 用 Go 1.27.4 编译（fib 提交 `42e6de6`），
  h2load（nghttp2）1.59.0。参照 crate：tokio 1.54、hyper 1.12（+ hyper-util `auto`）、
  tokio-tungstenite 0.28、tokio-rustls 0.26 / rustls 0.23（ring）。
- **安静主机**：所有测量都在 `quiet.sh run` 下进行：它加锁排除其他基准任务，停掉主机上的其他服务
  （一个推理服务、远程桌面、一个 kind 集群），把电源模式切到 `performance`（调速器 `performance`，
  boost 打开），跑完整套测试后再全部恢复。测试前负载均值 0.1。
- **绑核**：网络服务端在 CPU 0–3，4 个 I/O 线程（tokio：4 个 worker；fib：`GOMAXPROCS` 随 4 核亲和性）；
  压测端在 CPU 4–7 与 12–15，8 个线程；CPU 8–11（服务端核心的 SMT 兄弟线程）空闲。QUIC 的客户端与
  服务端在同一进程，绑 CPU 2–5；内存中与微基准绑 CPU 2。
- **轮次**：网络数字是 **3 轮的中位数**，每轮 5 秒，预热 1 秒（WebSocket：5 轮）；每一轮依次对每个
  服务端跑每个场景，每次都重新启动服务端。微基准：整个程序跑 3 次取中位数。`±` 是各轮最大最小值之差
  的一半占中位数的百分比，≤3% 时省略。echo、WebSocket 和内存各行来自一小时后用同一批二进制跑的第二遍：第一遍中
  有几个服务端没能绑定端口（见“复现”），修好测试脚本后重跑了这几项。
- **后端**：`only-epoll` 与 `only-uring` 是同一个服务端，分别用 `Backend::Epoll` 和 `Backend::IoUring`。
  QUIC/HTTP/3 有自己的 UDP 线程（不选后端），UDP echo 在两种后端下都走 epoll UDP 循环，所以这些行只有
  一列 `only`。
- **服务端**（处理逻辑一致）：`crates/only/examples/bench-server.rs`（TCP/TLS/UDP echo）和
  `crates/only-http/examples/http-bench.rs`（HTTP/1.1 + h2c + TLS 上的 h2，`/plaintext`、`/json`，
  `/ws` 上的 WebSocket echo）；参照实现在 `tools/bench-ref/`（`tokio-ref`、`hyper-ref`、`fib-ref`）。
  TLS 统一为 TLS 1.3 + ECDSA P-256 自签名证书（`only` 用 only-tls，tokio 用 tokio-rustls，fib 用
  `fib/tls`）。JSON：`only` 在示例里用一个手写的小序列化器，hyper 用 serde_json，fib 用 `encoding/json`。
- **压测工具**：HTTP/1.1 用 `h2load --h1`（主机上没有 wrk；流水线为 `-m 16`），HTTP/2 用 `h2load`
  （h2c 为 prior knowledge，TLS 上用 ALPN `h2`），echo（闭环）、TLS 握手（rustls 客户端）和内存测试
  （连接保持端）用仓库内的 `tools/echo-bench`。

### 局限

- **只走回环**：客户端与服务端在同一台机器上，共享内存带宽和内核回环路径；没有网卡、没有真实延迟、
  没有丢包。**DPDK 没有测**：主机上没有 DPDK 能驱动的网卡，`only-dpdk` 只通过进程内内存线路上的
  用户态 TCP/IP 协议栈出现。
- **h2load 上限**：8 线程的 h2load 最多约 400–500 万请求/秒。`only` 的 h2c 与 TLS 上 h2 的数字就在这个
  水平（服务端 4 个 CPU 跑满，但客户端也接近饱和），所以它们是 `only` 的下限。
- **受客户端限制的格子**：TLS 握手速率受客户端限制（8 个线程用 rustls 做每次握手的客户端一半）；
  keep-alive 的 HTTP/1.1 受内核限制（每个请求一次读一次写）。
- 参照服务端没有超出默认配置的调优。没有延迟分位数。

## 结果

### HTTP/1.1 与 HTTP/2（请求/秒）

HTTP/1.1：256 个连接。h2c 与 TLS 上的 h2：连接数 × 并发流数。

| 场景 | only-epoll | only-uring | hyper | fib |
|---|---:|---:|---:|---:|
| HTTP/1.1 `GET /plaintext` | 729,229 | 774,202 | 650,511 | 620,200 |
| HTTP/1.1 `GET /plaintext`，流水线 ×16 | 4,289,270 | 4,400,739 | 855,912 | 3,750,364 |
| HTTP/1.1 `GET /json` | 724,779 (±4%) | 771,332 | 633,300 | 594,476 |
| h2c，64 × 16 | 4,097,129 | 4,133,600 (±12%) | 1,031,686 | 3,231,636 |
| h2c，16 × 128 | 5,363,059 (±4%) | 4,896,627 (±11%) | 1,361,642 | 4,006,582 |
| TLS 1.3 上的 HTTP/2，64 × 16 | 3,975,030 (±7%) | 4,000,032 (±8%) | – ¹ | 3,049,105 |

¹ hyper-ref 没有 TLS 监听。

keep-alive HTTP/1.1 上 `only` 是 hyper 和 fib 的 1.1–1.25 倍；流水线时是 hyper 的 5 倍、fib 的
1.14–1.17 倍；h2c 是 hyper 的 3.6–4 倍、fib 的 1.22–1.34 倍；TLS 上的 HTTP/2 是 fib 的 1.3 倍
（受 h2load 上限约束，见“局限”）。

### 每连接内存

服务端 RSS 增量除以保持打开的连接数（`tools/bench/mem.sh`，3 轮，除注明外均在 ±1% 以内）：客户端
打开连接（分散在 127.0.0.1–4 上，使一个客户端能保持超过 6.4 万个连接），每个连接做一次交换，然后全部
保持空闲，此时读取服务端的 `VmRSS`。单位为每连接字节，除注明外为 10,000 个连接。这里 tokio 的每连接
读缓冲设为 4 KiB（`TOKIO_REF_BUF`）。

| 连接状态 | only-epoll | only-uring | tokio | hyper | fib |
|---|---:|---:|---:|---:|---:|
| 空闲 TCP（仅连接） | 603 | 603 | 5,008 | – | 280 |
| 空闲 TCP，**100,000 个连接** | 564 | 564 | 5,008 | – | 288 |

| 握手 + 一次 echo 之后的 TLS 1.3 | 8,192 | 8,186 | 15,124 | – | 6,815 |

² tokio-tungstenite 的默认配置为每个连接保留很大的读写缓冲。

³ 修复后重测（3 轮中位数，同一主机、同一套脚本）：本次测试的构建为 3,486（epoll）/ 3,485（uring）；
见“历史”一节末尾。

only-uring 预先分配其 provided-buffer 环（每个 I/O 线程 1024 × 16 KiB）：它的基线 RSS 约 69 MB，epoll

| TLS 1.3 完整握手/秒，X25519 | 5,496 | 5,464 | 5,030–5,062 | 1.09 | 1.08 |

改动：整点汇编改用 OpenSSL `ecp_nistz256` 的公式（加法 12M + 4S 配 7 次模加减，代替 11M + 5S 配 13 次；
混合加法 8M + 3S 配 7 次，代替 7M + 4S 配 14 次；倍点从 `2Y` 出发并用一次模减半：10 次线性运算代替 14 次），
约简每步从 10 条指令减为 7 条（`p₃` 留在 `rdx` 中，用 `rbx = 32` 做 `shlx`/`shrx`）。周期数（`perf stat`，
交替五轮取最小值）：倍点 355 → 348，加法 745 → 721，混合加法 537 → 508，可变基点乘法 148.1k → 140.6k，
经公开 API 的整个 ECDH（解码、乘法、求逆、编码）147.7k，固定基点梳形表 29.8k → 28.9k，域求逆 6.2k。握手没有
变化：一次 ECDH 约占一次握手的 1%。

用同样的测量尝试过但没有采用：调整倍点中乘积的顺序（先算独立的乘积，或先算 `Y` 链）慢 8–10%；OpenSSL 式
把约简交织进乘积各行持平（+1%）；把最终减法中的 `cmov` 选择换成 `xor`/`and` 掩码慢 10%。无论顺序如何，一次
倍点都表现为每个乘积约 44 个周期，接近它发出的 `mulx` 与读标志位指令的吞吐量，而不是它的依赖链长度。

#### 按消息长度的 AES-GCM（`--example gcm-sizes`，CPU 2）

消息字节的 MB/s，AAD 13 字节，三轮交替运行取中位数；优化前 = `main` 的 `a1cc9b49`（AES-NI +
PCLMULQDQ，每次归约 8 个分组），优化后 = VAES + VPCLMULQDQ + AVX-512 内核（每次循环与每次归约 16 个分组，
AES 轮函数与上一组的 GHASH 交织）加上融合的短尾部。解密前两边都先把密文复制进工作缓冲区。ring 0.17 在
这颗 CPU 上运行其 VAES/AVX2 内核。

位宽：在 Zen 4 上（512 位操作拆成两个 256 位半部执行），同一内核改用 256 位寄存器（每次迭代 8 个分组）在
所有长度上都更慢，因此只保留 512 位内核：AES-128 加密 16 KiB 15,100 对 13,100 MB/s，1 KiB 7,600 对
6,800，解密 16 KiB 13,150 对 11,775。短消息的提升来自尾部而不是位宽：消息的最后几个字节与 `J0` 一次
通过 AES，短 AAD、尾部密文与长度块一次通过 GHASH（之前是三次 GHASH 调用加一趟单独的 CTR），这让所有
具备 AES 与无进位乘法指令的 CPU 上 64 字节消息的速度翻倍。

剩下的差距：1 KiB 到 1.4 KiB 的 AES-GCM 消息为 ring 的 0.96–1.11 倍（宽内核的固定开销；最后一个 256 字节
组之后的尾部走 128 位路径）；有 VAES 但没有 AVX-512 的 CPU（Zen 3、Alder Lake）使用 128 位路径；TLS
记录层在 AEAD 写入之前仍先把输出清零（约占 16 KiB 记录的 9%）；Poly1305 是标量实现；P-256 ECDH 为
ring 的 1.12 倍（一次倍点约 348 个周期，无论顺序如何每个乘积约 44 个周期）；
Ed25519 验签是可移植实现；RSA 没有 Karatsuba；SHA-512 与 MD5 是可移植实现。

## 历史

各领域优化的简要总结；完整表格在本文件的 git 历史中。

- **2026-11-14，共享虚拟机**（笔记本上的 aarch64 Docker 虚拟机，有其他任务在跑，各轮波动 ±20–50%）：
  第一批跨库对比表。HPACK Huffman 解码表只建一次，h2c 从 29.2 万升到 187 万请求/秒（×6.4）；每次回调
  只读一次时钟、`Headers` 存进一个字符串、连接表用乘法哈希，HTTP/1.1 plaintext +9%、流水线 +17%；
  队列头内联、HTTP 会话状态装箱，TCP echo 后每连接内存 739 → 607 B，HTTP keep-alive 1,624 → 912 B。
- **HTTP 热路径**（本机，`main` 的 `df90c0b3` → 优化后）：h2 帧原地解析、解码的头部放进一个复用缓冲、
  HPACK 直接编码进输出、每次读只写一次、流控按四分之一窗口归还、HTTP/1 头部先用 32 个槽位解析。
  h2c 64 × 16 228 万 → 405 万（epoll），16 × 128 237 万 → 471 万，TLS 上的 HTTP/2 158 万 → 403 万
  （2.5 倍），流水线 HTTP/1.1 +7–8%，keep-alive HTTP/1.1 +1%（受内核限制）。优化前 `only` 的 HTTP/2 是
  fib 的 0.52–0.70 倍，本次测试为 1.22–1.34 倍。
- **密码学 CPU 加速**（本机，`354f3bc5` → 优化后）：AES-128-GCM 16 KiB 364 → 6,484 MB/s（17.8 倍），
  SHA-256 6.5 倍，SHA-1 3.6 倍，CRC-32 7.3 倍，ChaCha20-Poly1305 3 倍；P-256 签名 1.46 倍、验签 1.67 倍，
  Ed25519 验签 1.49 倍，RSA-2048 1.36–1.38 倍。TLS 记录快 9–15 倍，握手快 1.4–1.5 倍。
- **TLS 握手用的 P-256 与 X25519**（本机，CPU 2，交替运行三轮取中位数，`a1cc9b49` → 优化后）：P-256 的
  域运算与模群阶运算改为运行时检测的 BMI2/ADX 汇编，标量乘法改用 Jacobian 坐标（Booth 5 位窗口、有符号
  梳形表加混合加法），标量求逆使用专用加法链，X25519 公钥由 Edwards 基点表计算，阶梯使用 ADX。P-256
  签名 34,152 → 59,837 次/秒，验签 13,404 → 25,138，ECDH 10,380 → 27,288，生成密钥 54,581 → 108,263；
  X25519 30,696 → 36,488；Ed25519 签名 67,644 → 89,784；P-384 快 1.13–1.47 倍。握手 3,055 → 5,027 次/秒
  （X25519，rustls 的 1.00 倍）与 2,306 → 4,552 次/秒（secp256r1，0.89 倍）。
- **P-256 整点汇编**（本机，CPU 2，有负载时交替运行五轮取中位数，`7cefa48b` → 优化后）：倍点、加法与
  混合加法各为一个 `asm!` 块（五次倍点共用一个帧），固定基点改用 6 位 Booth 梳形表加 AVX2 扫表，ECDH
  窗口表用 AVX2 扫表，求逆改为 safegcd 加汇编 divsteps。与同一次运行中的 ring 相比：签名 0.77 倍 →
  1.25 倍，生成密钥 0.94 倍 → 1.33 倍，验签 0.98 倍 → 1.04 倍，ECDH 0.94 倍 → 0.96 倍；secp256r1 握手
  为 rustls 的 0.94 倍 → 1.12 倍。
- **P-256 点运算公式**（本机，CPU 2，空闲时交替运行五轮取中位数，`1376b324` → 优化后）：整点汇编改用
  OpenSSL `ecp_nistz256` 的加法、混合加法与倍点顺序，约简步骤更短。与同一次运行中的 ring 相比：ECDH
  1.08 倍 → 1.12 倍，签名 1.36 倍 → 1.38 倍，验签 1.08 倍 → 1.10 倍，生成密钥 1.36 倍 → 1.40 倍；握手不变
  （secp256r1 为 rustls 的 1.07 倍，X25519 为 1.08 倍）。
- **宽 AES-GCM 与 CRC**（本机，`a1cc9b49` → 优化后）：AES-GCM 改用 VAES + VPCLMULQDQ + AVX-512
  （512 位，经测量优于 256 位），16–64 KiB 快 2.3–2.5 倍（AES-128 加密 16 KiB 6,455 → 15,048 MB/s，
  相对 ring 0.51 倍 → 1.19 倍），融合尾部让 64 B 快 1.8–2.1 倍；TLS 1.3 记录非原地加解密，16 KiB 快
  2.4 倍（相对 rustls + ring 0.69 倍 → 1.65 倍）；CRC-32 在 512 位寄存器上折叠，16 KiB 19,992 →
  74,885 MB/s（相对 crc32fast 0.27 倍 → 1.02 倍）。
- **QUIC 与 TLS 热路径**（本机）：节拍器把 RTT 下限定为 1 ms 并为每个包唤醒发送方；改用测得的 RTT 并按
  突发量补充（与 quinn-proto 相同）后，批量传输 3.4–3.7 → 5.7 Gbit/s（quinn-proto 的 1.25 倍），HTTP/3
  17.1 万 → 42 万请求/秒（quinn-proto 的 7 倍）。TLS 记录直接在调用方缓冲区中解密：16–64 KiB +5–7%。
- **Deflate**（本机，wave A 匹配器 → zlib-ng 策略）：级别 2–9 压缩快 1.03–4 倍，级别 1 快 1.7–2.9 倍，
  解压快 1.1–1.45 倍；64 B 消息的 permessage-deflate echo 47.8 万 → 64.3 万次/秒。
- **用户态协议栈**（Apple 芯片笔记本，共享）：自研协议栈替换 smoltcp 0.12，批量吞吐 6.5–11 倍，顺序
  连接速率 11 倍。

本次测试在 1–2% 以内复现了 HTTP、QUIC、TLS、密码学和 deflate 各项优化的数字（这些方面没有退化）。
有一项内存数字变了：升级 + 一次 echo 之后的 WebSocket 连接这里是 3,493 字节，2026-11-14 的表中是 1,660
（其余各行与之相差不到 5%：空闲 TCP 600 → 603，HTTP keep-alive 912 → 937，TLS 8,526 → 8,192）。这是真实的
退化，与换主机无关：2026-11-14 的构建在本机用同一个 `mem.sh` 测得 1,683；二分定位到用 only-deflate 替换
flate2 的提交（1,679 → 3,437）。only-ws 的 permessage-deflate 包装把新的编解码状态内联保存（inflater
528 B，deflater 1,552 B；flate2 的状态在指针后面），而每个连接的解码器里都有一个 `Option<Inflater>`、
发送端里都有一个 `Option<Deflater>`，所以即使没有协商压缩（本基准就是这样）也要付出约 2 KB。现在状态
改为装箱：3,486 → 1,426 字节（epoll），3,485 → 1,414（uring），低于 2026-11-14 的数字。
