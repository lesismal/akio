# 基准测试

[English](BENCHMARKS.md) | 简体中文

2026-11-15 在一台安静的物理机上、基于同一个提交（`10070cff`，即各项自研替换和分领域性能优化之后：
密码学 CPU 加速、deflate、QUIC 节拍器、TLS 记录路径、h2 与 HTTP/1）跑的一次完整测试。下面所有表格
都来自这一次测试；此前各领域的优化前后数字压缩在[历史](#历史)一节。

## 主机与方法

- **主机**：AMD Ryzen 7 7800X3D（Zen 4，8 核 16 线程，最高 5.05 GHz，AES-NI、SHA-NI、PCLMULQDQ、
  VAES、AVX-512），61 GB 内存，Ubuntu 24.04，Linux 7.0.0-42，x86-64，非虚拟机。
- **工具链**：Rust 1.100.0（工作区的 release 配置），fib-ref 用 Go 1.27.4 编译（fib 提交 `42e6de6`），
  h2load（nghttp2）1.59.0。参照 crate：tokio 1.54、hyper 1.12（+ hyper-util `auto`）、
  tokio-tungstenite 0.28、tokio-rustls 0.26 / rustls 0.23（ring）。
- **安静主机**：所有测量都在 `quiet.sh run` 下进行：它加锁排除其他基准任务，停掉主机上的其他服务
  （一个推理服务、远程桌面、一个 kind 集群），把电源模式切到 `performance`（调速器 `performance`，
  boost 打开），跑完整套测试后再全部恢复。测试前负载均值 0.1。
- **绑核**：网络服务端在 CPU 0–3，4 个 I/O 线程（tokio：4 个 worker；fib：`GOMAXPROCS` 随 4 核亲和性）；
  压测端在 CPU 4–7 与 12–15，8 个线程；CPU 8–11（服务端核心的 SMT 兄弟线程）空闲。QUIC 的客户端与
  服务端在同一进程，绑 CPU 2–5；内存中与微基准绑 CPU 2。
- **轮次**：网络数字是 **3 轮的中位数**，每轮 5 秒，预热 1 秒（WebSocket：5 轮）；每一轮依次对每个
  服务端跑每个场景，每次都重新启动服务端。微基准：整个程序跑 3 次取中位数。`±` 是各轮最大最小值之差
  的一半占中位数的百分比，≤3% 时省略。echo、WebSocket 和内存各行来自一小时后用同一批二进制跑的第二遍：第一遍中
  有几个服务端没能绑定端口（见“复现”），修好测试脚本后重跑了这几项。
- **后端**：`only-epoll` 与 `only-uring` 是同一个服务端，分别用 `Backend::Epoll` 和 `Backend::IoUring`。
  QUIC/HTTP/3 有自己的 UDP 线程（不选后端），UDP echo 在两种后端下都走 epoll UDP 循环，所以这些行只有
  一列 `only`。
- **服务端**（处理逻辑一致）：`crates/only/examples/bench-server.rs`（TCP/TLS/UDP echo）和
  `crates/only-http/examples/http-bench.rs`（HTTP/1.1 + h2c + TLS 上的 h2，`/plaintext`、`/json`，
  `/ws` 上的 WebSocket echo）；参照实现在 `tools/bench-ref/`（`tokio-ref`、`hyper-ref`、`fib-ref`）。
  TLS 统一为 TLS 1.3 + ECDSA P-256 自签名证书（`only` 用 only-tls，tokio 用 tokio-rustls，fib 用
  `fib/tls`）。JSON：`only` 在示例里用一个手写的小序列化器，hyper 用 serde_json，fib 用 `encoding/json`。
- **压测工具**：HTTP/1.1 用 `h2load --h1`（主机上没有 wrk；流水线为 `-m 16`），HTTP/2 用 `h2load`
  （h2c 为 prior knowledge，TLS 上用 ALPN `h2`），echo（闭环）、TLS 握手（rustls 客户端）和内存测试
  （连接保持端）用仓库内的 `tools/echo-bench`。

### 局限

- **只走回环**：客户端与服务端在同一台机器上，共享内存带宽和内核回环路径；没有网卡、没有真实延迟、
  没有丢包。**DPDK 没有测**：主机上没有 DPDK 能驱动的网卡，`only-dpdk` 只通过进程内内存线路上的
  用户态 TCP/IP 协议栈出现。
- **h2load 上限**：8 线程的 h2load 最多约 400–500 万请求/秒。`only` 的 h2c 与 TLS 上 h2 的数字就在这个
  水平（服务端 4 个 CPU 跑满，但客户端也接近饱和），所以它们是 `only` 的下限。
- **受客户端限制的格子**：TLS 握手速率受客户端限制（8 个线程用 rustls 做每次握手的客户端一半）；
  keep-alive 的 HTTP/1.1 受内核限制（每个请求一次读一次写）。
- 参照服务端没有超出默认配置的调优。没有延迟分位数。

### HTTP/1.1 与 HTTP/2（请求/秒）

| HTTP/1.1 `GET /json` | 724,779 (±4%) | 771,332 | 633,300 | 594,476 |

SipHash 的版本与之对比，七轮）：批量传输 16,836 → 17,366 Mbit/s（+3%），HTTP/3 持平。

**HTTP/3 减少分配之后**（2026-11-16，同一主机与绑核，主机空闲，`62ea6318` → 优化后，交替运行七轮取中位数）：

| 场景 | 优化前 | 优化后 | 优化后 / 优化前 |
|---|---:|---:|---:|
| HTTP/3 GET，单连接，64 个并发 | 820,741 请求/秒（807,108–827,664） | 883,127 请求/秒（875,505–888,021） | 1.08 |

每个请求的内存分配次数（基准程序两端合计，用计数分配器统计）从 21.6 降到 8.6：流数据进入事件队列时不再
每次经过两个临时向量（每个请求 4 次）；较小的响应头与请求头写进 only-quic 的池化缓冲区，不再是一个 `Vec`
加上其 `Bytes` 的 `Arc`（4 次）；`Context` 自己持有请求，直到有需要共享时才放进 `Arc`（1 次）；64 字节及以上的
HEADERS 帧原地加宽长度字段，不再用 splice（1 次）；`Headers` 内联保存前两个字段的位置（3 次）。分配器在 profile
中的占比从 10.8% 降到 5.7%。QPACK 写 `:status`、`content-length` 与 date 行（每秒编码一次）时不再查静态表；
此前编码与解码各约占 profile 的 2%，现在在更短的单次请求里占比大致相同。剩下的分配是请求本身需要的（请求目标、
`Headers` 的缓冲区、响应体、装箱的响应 sink）。

only-http 的改动与 HTTP/1.1、HTTP/2 共用，在同一个空闲时段里做了检查（`http-bench`，服务端在 CPU 0–3，h2load
与上文表格相同，交替三轮；这几行受客户端或内核限制，所以 1200 万个请求下服务端每请求 CPU 时间是更稳定的指标）：

| 场景 | 请求/秒 优化前 → 优化后 | 优化后 / 优化前 | 服务端每请求 CPU 优化前 → 优化后 |
|---|---:|---:|---:|
| HTTP/1.1 `GET /plaintext` | 736,242 → 733,623 | 1.00 | 5,455 → 5,477 ns |
| HTTP/1.1 流水线 ×16 | 4,424,976 → 4,400,598 | 0.99 | 901 → 905 ns |
| h2c 64 × 16 | 4,328,640 → 4,297,478 | 0.99 | 925 → 926 ns |

均在多次运行之间的波动范围内（同一代码较早一个时段测得 HTTP/1.1 流水线为 899 ns，优化前为 903–908 ns）。
第一版内联保存四个字段位置：`Headers` 从 48 字节变成 80 字节，请求与响应因此多出的复制让 HTTP/2 的服务端每请求
CPU 增加约 3%；改为两个位置压进向量的 niche 后，它仍是 48 字节。

2,739 → 6,603 MB/s，相对 rustls + ring 0.69 倍 → 1.65 倍）。ChaCha20-Poly1305 记录运行在 AVX-512
ChaCha20 与 IFMA Poly1305 内核上，同样非原地加解密：16 KiB 时相对 rustls + ring 0.55 倍 → 1.42 倍（见下文）。

### 内核 TLS（kTLS）评估（`crates/only-tls/examples/ktls-bench.rs`、`tools/bench/ktls.sh`）

问题：only-tls 完成握手后，是否应把记录密钥交给 Linux 内核（`setsockopt(TCP_ULP, "tls")`，`SOL_TLS`
的 `TLS_TX` / `TLS_RX`），由内核加解密记录，让套接字上流动明文、让 `sendfile(2)` 在 TLS 下可用？
**结论：不应该。在这台主机上，内核的软件 kTLS 在所有测试情形下都比 only-tls 自己的记录层慢，而且恰恰在
它本该占优的地方（大响应与 `sendfile`）最慢。** 卸载代码保留在 only-tls 的 `experimental-ktls` feature
之后以便重新测量，没有接入 `Tls` 或引擎。

方法：一个每连接一线程的 TLS 上 HTTP/1.1 服务器（`ktls-bench`），记录层要么是用户态的 only-tls
（`user`：响应由 only-tls 加密后写出；文件用 `pread` 按 64 KiB 读入后加密），要么是内核（`ktls`：同样
由 only-tls 握手，然后交出密钥；响应以明文写出；文件用 `sendfile` 发送）。同一个二进制、同样的握手
（TLS 1.3、X25519、ECDSA P-256、无票据），除注明外均为 AES-128-GCM。服务器在 CPU 0–3，
`h2load --h1` 8 线程在 CPU 4–7 与 12–15，每次 2 s 预热后测 8 s，交替进行 3 轮（取中位数；各轮相差
1–2%），全部在 `quiet.sh` 下运行。Linux 7.0，Ryzen 7 7800X3D；内核的 AES-GCM 是
`generic-gcm-vaes-avx512`（与 only-crypto 同类的 VAES + AVX-512 代码），ChaCha20-Poly1305 是
`rfc7539(chacha20-lib,poly1305-generic)`。所有情形下服务器都是 CPU 瓶颈（每秒 4.0 CPU 秒），因此每字节
CPU 为服务器 CPU 时间（用户态 + 内核态，取自 `/proc`）除以发送的字节数。

| 情形（连接数） | only-tls 请求/秒 | kTLS 请求/秒 | kTLS / only | only-tls CPU ns/B | kTLS CPU ns/B | 每字节 CPU kTLS / only |
|---|---:|---:|---:|---:|---:|---:|
| 1 KiB 响应（64） | 531,393 | 439,368 | 0.83 | 6.77 | 8.55 | 1.26 |
| 16 KiB（64） | 358,494 | 233,814 | 0.65 | 0.679 | 1.042 | 1.53 |
| 256 KiB（32） | 66,057（16.1 GB/s） | 26,415（6.45 GB/s） | 0.40 | 0.231 | 0.577 | 2.50 |
| 10 MB 文件（16）：`pread` + 加密 对比 `sendfile` | 1,391（13.0 GB/s） | 669（6.24 GB/s） | 0.48 | 0.288 | 0.597 | 2.07 |
| 16 KiB，ChaCha20-Poly1305（64） | 284,155 | 175,070 | 0.62 | 0.858 | 1.393 | 1.62 |
| 16 KiB，TLS 1.2 AES-128-GCM（64） | 358,377 | 242,912 | 0.68 | 0.680 | 1.003 | 1.47 |

回环的 MTU 是 64 KiB；把客户端放进网络命名空间、经 MTU 1500 的 veth 对连接（`VETH=1`，GSO/GRO 开启，
与网卡相同）时比值不变：0.83（1 KiB）、0.65（16 KiB）、0.40（256 KiB）、0.49（文件）。卸载本身每连接
花费 14–20 µs（`TCP_ULP` 加两次 `SOL_TLS` 设置密钥），而一次完整握手两端合计约 200 µs CPU（`tls-bench`
中每秒 5,027 次）：对短连接是不可忽视的额外开销。

原因（perf，10 MB 文件情形）：使用 kTLS 时，服务器 96% 的采样位于 `tls_sw_sendmsg` 之下，但 AES-GCM
本身只占约 12%。内核把每条 16 KiB 记录单独推给 TCP（`tls_push_record` → `tcp_push`：约 55% 的采样在
TCP/IP 发送路径中，包括回环的接收软中断；用户态每次 `write` 交给 TCP 64 KiB 的记录，只占约 29%），并为
每条记录分配并清零新页（`kernel_init_pages` 约 5%）。在用户态，同样的工作是 only-crypto 的 GCM（22%）
加上 `pread` 与 `write` 的拷贝（各约 14%）；省掉这些拷贝抵不上内核中每条记录的开销。小响应损失较小
（0.83 倍），因为每个请求的开销主要是两种模式共有的系统调用与 TCP。

kTLS 仍可能划算的情况：带 TLS 卸载的网卡（`tls-hw-tx-offload`，如 ConnectX-6 Dx；本机没有），此时内核
把未加密的记录交给网卡，`sendfile` 才真正零拷贝；或者用户态 AES-GCM 比内核慢得多的主机（没有 VAES）。
这两种情况都不适用于 x86_64 上带 VAES 的 only-tls；重新考虑之前请先用 `tools/bench/ktls.sh` 重新测量。

实验代码覆盖的内容（测试：在支持 kTLS 的内核上运行 `crates/only-tls/tests/ktls.rs`，内存中的单元测试
随处可跑；`ONLY_INTEROP_KTLS=require tools/interop/tls/run.sh` 在 only 一侧卸载的情况下对 OpenSSL
3.0.13 与 Go 1.27 通过 107/107）：TLS 1.3 与 1.2 的 AES-128-GCM、AES-256-GCM 与 ChaCha20-Poly1305；
握手后导出密钥与序列号（仅当没有任何缓冲数据时）；通过记录类型控制消息收发告警、close_notify 与握手后
消息（NewSessionTicket、KeyUpdate）；通过重新安装密钥实现双向 TLS 1.3 KeyUpdate（Linux 6.14+；更旧的
内核让 TLS 1.3 留在用户态，因为对端随时可能更新密钥）；`tls` 模块或套件缺失时回退到用户态。未做：引擎
集成（epoll / io_uring 接收时处理 `TLS_GET_RECORD_TYPE`、写队列中的控制记录）、`TLS_RX_EXPECT_NO_PAD`，
以及在 AES-GCM 记录数上限之前主动发送 KeyUpdate（内核不替我们计数）。

### io_uring 特性评估（`tools/bench/uring-eval.sh`、引擎 A/B）

2026-11-16 测量。问题（DEV-PLAN M2）：io_uring 后端是否应使用注册文件、`SEND_ZC`、`MSG_RING` 唤醒或基于 ring 的发送？
规则：只有同一轮内 A/B 明确提升至少 3%、且其他场景没有退步时才采用。**结论：目前一个都不采用。**
基于 ring 的发送是唯一有真实信号的（在裸 ring 上每请求服务器 CPU 少 2–7%），但引擎从任意线程直接写
socket，用它意味着重新设计写路径，而不是打开一个开关。`SEND_ZC` 在回环上全面落后；其他几项都在噪声
范围内。Linux 7.0，Ryzen 7 7800X3D，全部在 `quiet.sh` 下运行，服务器在 CPU 0–3（4 线程），`h2load` /
`echo-bench` 用 8 线程跑在 CPU 4–7 与 12–15；后端已经使用 multishot accept 与 recv、provided-buffer
ring，以及 `COOP_TASKRUN` + `SINGLE_ISSUER` + `DEFER_TASKRUN` 的 ring。

**在裸 ring 上比较发送方式。** 不做上述重新设计，引擎无法改用 ring 发送，所以这部分在一个直接驱动
only-uring ring 的最小 HTTP/1.1 应答程序上测量（被忽略的 `eval_server` 测试，
`crates/only-uring/src/eval.rs`）：与后端相同的 multishot accept 和 recv，每个请求从一个静态缓冲区回一个
固定响应（因此 `SEND_ZC` 永远不必等缓冲区归还：这是它的最好情况），发送方式为在完成事件处理中调用
`write(2)`（引擎的做法）、随下一次等待一起提交的 `IORING_OP_SEND` 条目，或 `IORING_OP_SEND_ZC`；
“+fixed” 表示 direct accept 进注册文件表，并在每个条目上设 `IOSQE_FIXED_FILE`。256 连接，5 轮交错、
每轮 5 秒，取中位数；吞吐量相对 `write`，以及每请求的服务器 CPU（用户态 + 内核态，取自 `/proc`）。

| 响应（每连接在途请求数） | `write` 请求/秒 | SEND | SEND +fixed | SEND_ZC | SEND_ZC +fixed | 每请求 CPU µs：write / SEND / +fixed / ZC |
|---|---:|---:|---:|---:|---:|---|
| 13 B 正文（16，pipelined） | 9,011,289 | 1.038 | 1.066 | 0.885 | 0.911 | 0.333 / 0.312 / 0.309 / 0.366 |
| 1 KiB（16，pipelined） | 7,302,214 | 1.035 | 1.046 | 0.880 | 0.866 | 0.546 / 0.527 / 0.525 / 0.622 |
| 16 KiB（1） | 495,080 | 1.033 | 1.039 | 0.877 | 0.881 | 8.08 / 7.82 / 7.79 / 9.20 |
| 64 KiB（1） | 296,010 | 1.018 | 1.025 | 0.768 | 0.772 | 13.52 / 13.27 / 13.21 / 17.64 |
| 256 KiB（1） | 110,173 | 1.011 | 1.016 | 0.733 | 0.738 | 36.3 / 35.8 / 35.8 / 49.5 |

- **`SEND_ZC`：不采用。** 慢 12–27%，每请求 CPU 多 10–36%，在它本该擅长的大响应上最差。打开
  `IORING_SEND_ZC_REPORT_USAGE` 后，每个通知都表明内核拷贝了数据：回环（以及 veth 对）无法把页直接交给
  接收方，零拷贝变成了一次拷贝加页面钉住再加每次发送多一个完成事件。它只可能在真实网卡、16 KiB 及以上
  的响应上胜出，而且那时需要把发送缓冲区一直保留到通知到达，引擎的写队列并不这样做。请在有网卡的
  主机上用 `tools/bench/uring-eval.sh` 重新测量。
- **基于 ring 的发送（`IORING_OP_SEND`）：目前不采用；是唯一值得单独立项的候选。** 比 `write(2)`
  吞吐量高 1–4%，每请求 CPU 少 2–6%，小响应收益最大（一整批完成事件产生的发送，随事件循环本来就要做的
  那一次 `io_uring_enter` 一起交给内核）。在引擎中，任意线程的 `Conn::send` 都直接写 socket、只把剩余部分
  入队，而这条写路径与 epoll 共用；ring 发送要求字节在完成前一直被持有、每连接只有一个在途发送，并与
  其他线程的直接写保持顺序。对 HTTP 服务器而言，每个 pipelined 请求省下约 0.02 µs，约为它每请求 CPU 的
  2–3%（4 核 450 万请求/秒时每请求 0.9 µs），达不到门槛。
- **注册文件（direct accept、`IOSQE_FIXED_FILE`）：不采用。** 在 ring 发送之上再提升 0.4–2.7%。在引擎
  中它们没有可节省的东西：对一次 plaintext 运行（230 万请求，pipelined 时 1360 万）统计提交条目，总共
  只有 520 个，即每连接两个（multishot recv 与复位监视）加上事件循环自己的；稳态下后端每个请求不提交
  任何条目，每请求仅有的系统调用是写响应的 `write` 和一次共享的 `io_uring_enter`。direct 描述符也没有
  普通 fd，而其他线程的直接 `write` 路径需要它。

**引擎 A/B**（对 reactor 的临时补丁，用环境变量切换，每轮两种变体都跑，每次运行用新启动的服务器，
`http-bench` / `bench-server`）：

| 场景 | 注册 ring fd（5 轮） | `MSG_RING` 唤醒，第 1 次（5 轮） | `MSG_RING`，第 2 次（7 轮） |
|---|---:|---:|---:|
| HTTP/1.1 plaintext，256 连接 | 0.985 | 0.995 | 1.002 |
| HTTP/1.1 pipelined 16 x 256 | 1.000 | 1.002 | 1.001 |
| TCP echo 64 B x 256 | 0.964 | 0.964 | 0.974 |
| TCP echo 16 KiB x 256 | 0.982 | 1.044 | 0.983 |
| `spawn_blocking` echo（`block-pool 0`），64 B x 256 | 1.005 | 1.048 | 1.030 |
| `spawn_blocking` echo，64 B x 64 | | | 0.987 |
| `spawn_blocking` echo，1 KiB x 256 | | | 1.015 |

- **注册 ring fd（`IORING_REGISTER_RING_FDS` + `IORING_ENTER_REGISTERED_RING`）：不采用。** 它省掉每次
  `io_uring_enter` 的 fd 查找，而 256 连接时事件循环大约每 20 个请求才 enter 一次：−3.6% 到 +0.5%，
  即噪声（在这台主机上普通 echo 各行在轮次之间浮动 ±10%）。
- **`MSG_RING` 唤醒：不采用。** 其他线程（完成 `spawn_blocking` 的线程池线程、跨线程的 `close`）通过写
  eventfd 唤醒事件循环，由 ring 上挂着的 `read` 完成；借助 `IORING_REGISTER_SEND_MSG_RING`（6.13+），
  没有 ring 的线程也能把完成事件直接投进事件循环的 CQ，事件循环不必再重新挂上 eventfd 的读。它能工作
  （strace：2 秒的线程池 echo 中，8,949 次 `io_uring_register` 取代了 5,558 次 eventfd 写），但收益只出现在
  唤醒占主导的场景，而且不明确：256 连接 64 B 线程池 echo +3.0–4.8%，1 KiB +1.5%，64 连接 −1.3%；线程池
  往返的开销主要是线程池自己的 futex 唤醒（约占服务器系统调用时间的 94%）。跨线程的 `Conn::send` 除非
  socket 写满，否则根本不需要唤醒（它直接写），因此没有收益。
- **已在使用**：`COOP_TASKRUN`、`SINGLE_ISSUER`、`DEFER_TASKRUN`（被拒绝时有回退）、multishot accept
  与 recv、provided-buffer ring；`SQPOLL` 需显式开启（`UringConfig::sqpoll`）。注册缓冲区只会服务于
  `SEND_ZC`（固定发送缓冲区）或 `READ_FIXED`；在 provided buffers 上的 multishot recv 加直接写的模式下，
  没有需要注册的东西。recv bundle 与增量缓冲区消费没有尝试。

#### IFMA 上的 RSA 验签（`--example pk_bench rsa`、`tls-bench handshakes`，CPU 2）

公开运算 `sᵉ mod n`（验签，以及每个签名发出前的校验）现在也在 AVX-512 IFMA 上计算，对 `e` 从高位到低位
平方-乘：为公开模数新增两个单模数 AMM，`amm64`（3,072 位：每个数用 8 个 `zmm` 寄存器，操作数补零到 64
个数字、只走 60 个数字步）与 `amm80`（4,096 位：每个数 10 个寄存器，用掉 32 个中的 30 个，因此最高寄存器
靠零掩码移入零通道，输出指针暂存在 `k7`，常量在循环结束后放进 `m` 的寄存器，最后的进位传播分两个字处理
80 个通道）；2,048 位沿用已有的 `amm40`。用一次乘以 `R'² mod n` 的 AMM 进入 `2^(52D)` 形式（`R'² mod n`
由 `R² mod n` 经一次短除法得到），最后一次乘法乘的是 `s` 而不是 `s·R'`，同时离开该形式：`e = 65537` 共 18

长除法得到（不再做 Montgomery 乘法），而长除法的每个商数字改用除数最高 limb 的预计算倒数（Möller–Granlund）

改动：

- **整条消息都在 AVX-512 内核里完成。** 不超过 256 字节的 AAD 在内核里做 GHASH；最后一个不完整的组
  （1 到 255 字节）用 AVX-512 字节掩码（k1–k4，被掩掉的字节既不读也不写）加载与存储，并用 `Hⁿ … H¹`
  做 GHASH——幂次通过指向幂次表的指针选取，幂次表后面补了 16 个零项，4 个向量加载永远不会越界；长度块与
  `E(J0)`（在开头用一个 lane 计算，与第一组重叠）在同一次调用里给出标签。AAD、数据与长度块合计不超过 16
  个分组的 256 字节以下消息走短路径：它们全部乘以 `Hᵀ … H¹` 后只做一次归约，AAD 与（解密时）密文的乘积
  与 AES 轮函数重叠，两者都不超过 64 字节时各只用一个向量。没有短路径的第一版在 64 B 上慢了 7%（AAD、
  数据、长度块三次相互依赖的归约），1 KiB 上同样快 32%；短路径把 64 B 从 1,112 提升到 1,383 MB/s。
- **VAES-AVX2 内核**，供没有 AVX-512 的 CPU 使用：CPUID 报告 VAES + VPCLMULQDQ + AVX2 且操作系统保存
  YMM 状态、但没有 AVX-512 时选用。每次迭代用 8 个 ymm 寄存器处理 16 个分组，AES 轮函数与上一组（加密）或
  同一组（解密）的 GHASH 交织，每 16 个分组一次归约。VEX 只有 16 个向量寄存器，所以轮密钥每轮从内存广播，
  常量作为内存操作数。每次迭代 8 个分组（4 个 ymm 状态）更慢：加密 16 KiB 11,540 对 12,660 MB/s，1 KiB
  6,530 对 6,890，解密相差 1% 以内（4 个独立的 AES 状态填不满两条 AES 流水线的延迟）。它只处理完整的 256
  字节组，消息其余部分走 128 位路径。在本机上与 ring 自己的 VAES-AVX2 代码相比为 0.86 倍（加密 1 KiB）到
  1.11 倍（加密 64 B），16 KiB 为 0.94 倍。
- **TLS 记录的预先清零：当时保留，现已去掉**（only-crypto 中的一步 `unsafe`，见下文“去掉 TLS 记录的预先
  清零”）。同一次运行中测量（三轮交替，AES-128-GCM，加密 + 解密 MB/s）：现有代码
  （先清零，再由 AEAD 非原地写入）16 KiB 6,620 / 6,675；把明文复制进记录再原地加密 6,256 / 6,259（−6%；
  64 KiB −8%，1 KiB −2%）；仅作参考、未提交的 `unsafe` `set_len` 去掉清零 7,297 / 7,313（+10%；64 KiB
  +8%，1 KiB +4%）。记录层跨记录复用缓冲区只是把 memset 换成 memcpy，开销与复制方案相同。输出是调用方的
  `Vec<u8>`、only-tls 又是 `#![forbid(unsafe_code)]`，任何安全方案都要把输出写两遍，因此保留清零（较便宜的
  第二次写入）；去掉它需要那一步 `unsafe`。ChaCha20-Poly1305 的 1 KiB 记录用复制加原地加密快 7%（ChaCha
  的非原地路径在短消息上开销更大），16–64 KiB 持平或更慢；未改动。

ChaCha20-Poly1305 非原地路径在短记录上的额外开销（上文提到 1 KiB 时复制加原地加密更快）基本消失：与先复制进
向量再原地加密相比，`append` 在 64 B 时为 −1.5%（406 对 412 MB/s），256 B 与 1 KiB 持平，16 KiB 为 +6%；
`from` 在 64 B 时为 −4.4%。原地的 AES-GCM 与 ChaCha20-Poly1305（前面各小节中 `gcm-sizes` / `chacha-sizes`
的同一些行）在两个版本之间变化 −2.2% 到 +4.7%，在本机运行间的波动之内；一个中间版本的 `Fill` 辅助函数没有
`#[inline]`，64 字节原地消息（128 位 AES-GCM 加密、ChaCha20-Poly1305 解密）慢 4–6%，最终版本没有这一现象。

#### ChaCha20-Poly1305 短消息（`--example chacha-sizes`，`tls-bench records`，CPU 2）

约 1.4 KiB 以下的消息低于 ring（64 B 为 0.83 倍，1 KiB 为 0.94–1.00 倍）：短消息就是一次受延迟限制的加密调用
加一次标量 Poly1305，64 字节加密的剖析中 62% 是生成 Poly1305 密钥与前三个消息分组的四分组 xmm 调用（每轮约
21 个周期：16 个寄存器，四个分组每轮 48 条指令）。改动：

- 四个分组改为每个 zmm 寄存器存放每个分组的一行（OpenSSL 的布局：列轮，用 `vpshufd` 把对角线转成列，对角
  轮，再转回）：每轮 15 条指令而不是 48 条，依赖链长度大致相同。它取代了 xmm 内核，用于消息开头与不超过四个
  分组的尾部。保留：按字切分的 ymm（八个分组）与 zmm（十六个分组）内核。两组行并排的八分组内核比 ymm 内核慢
  （只算 ChaCha20，512 B：每次调用 127 对 108 ns）。
- 最后一个不完整的组改为在 AVX-512 BW 字节掩码下直接经内核处理，不再经清零的 1 KiB 缓冲区和两次复制。该组中的
  整分组仍用普通加载与存储：第一个版本对组内每个分组都用掩码，缓冲区不是 64 字节对齐时 16 KiB 慢 5–8%（在
  Zen 4 上，跨缓存行的带掩码访问要几十个周期）。
- 消息开头取四个或八个分组，按实测的内核耗时（一组行约 63 ns，ymm 组 83 ns，zmm 组 140 ns）选剩余部分更便宜
  的一种：256 B 与 1400 B 因此少一次调用。
- AEAD 的 Poly1305 直接吸收补零后的 AAD、密文与长度块（不完整分组用定长复制），不再经过流式缓冲区：几个字节
  不再调用 `memcpy`。

#### AVX2 上的 Poly1305（`--example chacha-sizes`，`avx2` 密钥，CPU 2）

有 AVX2 但没有 AVX-512 IFMA 的 CPU（Zen 2 与 Zen 3、大多数 Intel 客户端处理器）原先用 2⁶⁴ 进制标量循环计算
Poly1305。现在对 512 字节及以上的连续分组，Poly1305 在 AVX2 上以 2²⁶ 为基数每步吸收四个分组（poly1305-donna /
OpenSSL 的布局：每个寄存器存放四个累加器的第 `j` 个肢，每步 25 条 `vpmuludq`，每步乘以 `r⁴`，最后一步按通道分别乘以
`r⁴, r², r³, r`）；更短时计算 `r` 的幂次的开销超过内核节省的时间（用内核时 256–448 B 慢 3–10%）。两组累加器（每步
八个分组）超出了 16 个 ymm 寄存器，反而更慢。编写差分测试时发现，把各通道之和转回 2⁶⁴ 进制需要再完整进位一遍
（`r = 1` 且分组全为 1 时，进位会一直传到第 128 位）。

在 Zen 4 上通过 AVX2 密钥测量（`ChaCha20Poly1305::new_avx2`：AVX2 ChaCha20，现在加上 AVX2 Poly1305；手头没有不带
AVX-512 的机器），与 `main` 交替运行五轮取中位数，MB/s：加密 1 KiB 1,654 → 1,767（+6.8%），1400 B 1,998 → 2,200
（+10.1%），16 KiB 2,270 → 2,729（+20.2%），64 KiB 2,311 → 2,795（+20.9%）；解密 16 KiB 2,190 → 2,617
（+19.5%）。默认路径（AVX-512 + IFMA）、可移植实现以及 512 字节以下的消息不变。

## 历史

各领域优化的简要总结；完整表格在本文件的 git 历史中。

- **2026-11-14，共享虚拟机**（笔记本上的 aarch64 Docker 虚拟机，有其他任务在跑，各轮波动 ±20–50%）：
  第一批跨库对比表。HPACK Huffman 解码表只建一次，h2c 从 29.2 万升到 187 万请求/秒（×6.4）；每次回调
  只读一次时钟、`Headers` 存进一个字符串、连接表用乘法哈希，HTTP/1.1 plaintext +9%、流水线 +17%；
  队列头内联、HTTP 会话状态装箱，TCP echo 后每连接内存 739 → 607 B，HTTP keep-alive 1,624 → 912 B。
- **HTTP 热路径**（本机，`main` 的 `df90c0b3` → 优化后）：h2 帧原地解析、解码的头部放进一个复用缓冲、
  HPACK 直接编码进输出、每次读只写一次、流控按四分之一窗口归还、HTTP/1 头部先用 32 个槽位解析。
  h2c 64 × 16 228 万 → 405 万（epoll），16 × 128 237 万 → 471 万，TLS 上的 HTTP/2 158 万 → 403 万
  （2.5 倍），流水线 HTTP/1.1 +7–8%，keep-alive HTTP/1.1 +1%（受内核限制）。优化前 `only` 的 HTTP/2 是
  fib 的 0.52–0.70 倍，本次测试为 1.22–1.34 倍。
- **密码学 CPU 加速**（本机，`354f3bc5` → 优化后）：AES-128-GCM 16 KiB 364 → 6,484 MB/s（17.8 倍），
  SHA-256 6.5 倍，SHA-1 3.6 倍，CRC-32 7.3 倍，ChaCha20-Poly1305 3 倍；P-256 签名 1.46 倍、验签 1.67 倍，
  Ed25519 验签 1.49 倍，RSA-2048 1.36–1.38 倍。TLS 记录快 9–15 倍，握手快 1.4–1.5 倍。
- **TLS 握手用的 P-256 与 X25519**（本机，CPU 2，交替运行三轮取中位数，`a1cc9b49` → 优化后）：P-256 的
  域运算与模群阶运算改为运行时检测的 BMI2/ADX 汇编，标量乘法改用 Jacobian 坐标（Booth 5 位窗口、有符号
  梳形表加混合加法），标量求逆使用专用加法链，X25519 公钥由 Edwards 基点表计算，阶梯使用 ADX。P-256
  签名 34,152 → 59,837 次/秒，验签 13,404 → 25,138，ECDH 10,380 → 27,288，生成密钥 54,581 → 108,263；
  X25519 30,696 → 36,488；Ed25519 签名 67,644 → 89,784；P-384 快 1.13–1.47 倍。握手 3,055 → 5,027 次/秒
  （X25519，rustls 的 1.00 倍）与 2,306 → 4,552 次/秒（secp256r1，0.89 倍）。
- **P-256 整点汇编**（本机，CPU 2，有负载时交替运行五轮取中位数，`7cefa48b` → 优化后）：倍点、加法与
  混合加法各为一个 `asm!` 块（五次倍点共用一个帧），固定基点改用 6 位 Booth 梳形表加 AVX2 扫表，ECDH
  窗口表用 AVX2 扫表，求逆改为 safegcd 加汇编 divsteps。与同一次运行中的 ring 相比：签名 0.77 倍 →
  1.25 倍，生成密钥 0.94 倍 → 1.33 倍，验签 0.98 倍 → 1.04 倍，ECDH 0.94 倍 → 0.96 倍；secp256r1 握手
  为 rustls 的 0.94 倍 → 1.12 倍。
- **QUIC 数据通路**（本机，CPU 2–5，新旧同轮交替，`42d67dde` → 优化后）：默认开启 UDP GRO（批量传输
  6.4 → 9.8 Gbit/s：一批 GSO 数据一次接收，途中不再 `skb_segment`），借助 UDP 循环内部的批次结束钩子
  每个接收批次只生成一次 ACK（9.5 → 13.6 Gbit/s），已发送包改用环形缓冲、收到的包使用池化缓冲区
  （14.3 → 15.1），UDP 循环每个数据报读一次时钟而不是三次、QUIC 定时器每批只设置一次（15.2 → 16.2）。
  HTTP/3 +3–4%，握手持平。64 字节 UDP echo 开关 GRO 各交替 15 轮：在该场景的噪声范围内（64 个对端时
  ±15%；单个请求在途时 −0.3% 到 −0.9%）。
- **HTTP/3**（本机，CPU 2–5，新旧同轮交替，`dbc7563f` → 优化后）：帧原地读取，字段段解码进一个复用缓冲区
  再复制一次进 `Headers`，HEADERS 直接用 QPACK 编码进输出、每个响应只写一次 QUIC，静态表查找不再用
  SipHash 映射（44.5 万 → 73 万请求/秒）；按序到达的流 ACK 不经过区间树（+3.5%），一次收全的请求不进流表
  （+2.5%），QPACK 整数内联（+2%），流的第一块发送数据内联（+3%），响应头一次分配好（+1%）。合计 42.9 万 →
  83.9 万请求/秒（1.95 倍）。only-quic 的连接 ID 表、连接表与对端地址表改用带密钥的乘法折叠哈希代替
  SipHash：批量传输 +3%。
- **P-256 点运算公式**（本机，CPU 2，空闲时交替运行五轮取中位数，`1376b324` → 优化后）：整点汇编改用
  OpenSSL `ecp_nistz256` 的加法、混合加法与倍点顺序，约简步骤更短。与同一次运行中的 ring 相比：ECDH
  1.08 倍 → 1.12 倍，签名 1.36 倍 → 1.38 倍，验签 1.08 倍 → 1.10 倍，生成密钥 1.36 倍 → 1.40 倍；握手不变
  （secp256r1 为 rustls 的 1.07 倍，X25519 为 1.08 倍）。
- **RSA**（本机，CPU 2，空闲机器上交替运行三轮，`7f5c483a` → 优化后）：BMI2 + ADX 的 Montgomery 乘法与
  平方汇编，基于 AVX-512 IFMA（基数 2⁵²）的模幂，带一遍式 AVX2 查表的 5 位窗口，用平方或一次除法计算 `R²`。
  对比 ring：RSA-2048 签名 0.49 倍 → 1.61 倍，3072 位 0.47 倍 → 1.85 倍，4096 位 0.45 倍 → 2.19 倍，验签
  0.60 倍 → 1.22 倍，含密钥解析的验签 0.09 倍 → 1.02 倍；使用 RSA-2048 证书的握手为 rustls 的 0.43 倍 →
  1.44 倍。
- **RSA 的 CRT 两半交错**（本机，CPU 2，`a965d26c` → 优化后）：一次签名的两个半模幂放进同一个 IFMA 循环，
  两条约简链重叠。对比 ring：RSA-2048 签名 1.63 倍 → 2.20 倍，3072 位 1.87 倍 → 2.19 倍，4096 位 2.21 倍 →
  2.55 倍；使用 RSA-2048 证书的握手为 rustls 的 1.45 倍 → 1.69 倍；验签不变。
- **IFMA 上的 RSA 验签**（本机，CPU 2，`62ea6318` → 优化后）：公开运算以 2⁵² 为基数计算（新增 3,072 与
  4,096 位 AMM），`e = 65537` 只需 18 次乘积，`R²` 用更快的除法求得。对比 ring：验签 1.22 → 3.07 倍 /
  1.10 → 3.30 倍 / 1.09 → 3.70 倍（2048 / 3072 / 4096），含密钥解析 1.02 → 2.35 倍 / 0.95 → 2.64 倍 /
  0.95 → 2.90 倍；签名 2.26 / 2.24 / 2.60 倍；使用 RSA-2048 证书的握手为 rustls 的 1.67 倍 → 1.82 倍。
- **宽 AES-GCM 与 CRC**（本机，`a1cc9b49` → 优化后）：AES-GCM 改用 VAES + VPCLMULQDQ + AVX-512
  （512 位，经测量优于 256 位），16–64 KiB 快 2.3–2.5 倍（AES-128 加密 16 KiB 6,455 → 15,048 MB/s，
  相对 ring 0.51 倍 → 1.19 倍），融合尾部让 64 B 快 1.8–2.1 倍；TLS 1.3 记录非原地加解密，16 KiB 快
  2.4 倍（相对 rustls + ring 0.69 倍 → 1.65 倍）；CRC-32 在 512 位寄存器上折叠，16 KiB 19,992 →
  74,885 MB/s（相对 crc32fast 0.27 倍 → 1.02 倍）。
- **AES-GCM 遗留项**（本机，`dbc7563f` → 优化后）：AVX-512 内核处理整条消息（AAD、带掩码的最后一个不完整
  组、长度块与 `E(J0)`；短消息只做一次归约）：AES-128 加密 1 KiB 为 ring 的 1.00 倍 → 1.32 倍，1400 B
  1.10 倍 → 1.46 倍，64 B 1.11 倍 → 1.29 倍，解密 1 KiB 1.04 倍 → 1.22 倍；为没有 AVX-512 的 CPU 新增
  VAES-AVX2 内核（8 个 ymm 处理 16 个分组），在 Zen 4 上为 128 位内核的 1.55–2.35 倍；TLS 1.3 记录 1 KiB
  为 rustls + ring 的 1.51 倍 → 1.58 倍。记录的预先清零保留（测过的安全替代方案都更慢）。
- **去掉 TLS 记录的预先清零**（本机，`f34c79e3` → 改动后）：记录层直接在输出向量的空闲容量中加密和解密
  （only-crypto 的 `encrypt_append` / `decrypt_append`，一个很小的 `unsafe` 模块；only-tls 仍是
  `forbid(unsafe_code)`）：TLS 1.3 记录 AES-128-GCM +6.9–8.3%（16 KiB 为 rustls + ring 的 1.58 倍 → 1.72 倍），
  AES-256-GCM +7.4–8.7%，ChaCha20-Poly1305 +3.3–6.4%；单独的 AEAD 非原地运行在 VAES-AVX-512 上 1–64 KiB
  快 10–11%。
- **QUIC 与 TLS 热路径**（本机）：节拍器把 RTT 下限定为 1 ms 并为每个包唤醒发送方；改用测得的 RTT 并按
  突发量补充（与 quinn-proto 相同）后，批量传输 3.4–3.7 → 5.7 Gbit/s（quinn-proto 的 1.25 倍），HTTP/3
  17.1 万 → 42 万请求/秒（quinn-proto 的 7 倍）。TLS 记录直接在调用方缓冲区中解密：16–64 KiB +5–7%。
- **Deflate**（本机，wave A 匹配器 → zlib-ng 策略）：级别 2–9 压缩快 1.03–4 倍，级别 1 快 1.7–2.9 倍，
  解压快 1.1–1.45 倍；64 B 消息的 permessage-deflate echo 47.8 万 → 64.3 万次/秒。
- **用户态协议栈**（Apple 芯片笔记本，共享）：自研协议栈替换 smoltcp 0.12，批量吞吐 6.5–11 倍，顺序
  连接速率 11 倍。

本次测试在 1–2% 以内复现了 HTTP、QUIC、TLS、密码学和 deflate 各项优化的数字（这些方面没有退化）。
有一项内存数字变了：升级 + 一次 echo 之后的 WebSocket 连接这里是 3,493 字节，2026-11-14 的表中是 1,660
（其余各行与之相差不到 5%：空闲 TCP 600 → 603，HTTP keep-alive 912 → 937，TLS 8,526 → 8,192）。这是真实的
退化，与换主机无关：2026-11-14 的构建在本机用同一个 `mem.sh` 测得 1,683；二分定位到用 only-deflate 替换
flate2 的提交（1,679 → 3,437）。only-ws 的 permessage-deflate 包装把新的编解码状态内联保存（inflater
528 B，deflater 1,552 B；flate2 的状态在指针后面），而每个连接的解码器里都有一个 `Option<Inflater>`、
发送端里都有一个 `Option<Deflater>`，所以即使没有协商压缩（本基准就是这样）也要付出约 2 KB。现在状态
改为装箱：3,486 → 1,426 字节（epoll），3,485 → 1,414（uring），低于 2026-11-14 的数字。

## 复现

见 [tools/bench/README.zh-CN.md](../tools/bench/README.zh-CN.md)。简而言之，在装有 h2load、Go 和 fib
检出的 Linux 主机上：

```sh
export CARGO_TARGET_DIR=/path/to/target
FIB_SRC=/path/to/fib tools/bench/build.sh
SRV_CPUS=0-3 CLI_CPUS=4-7,12-15 THREADS=4 CLI_THREADS=8 SECS=5 RUNS=3 \
  tools/bench/http.sh plaintext,pipelined,json,h2,h2many,h2tls,ws
SRV_CPUS=0-3 CLI_CPUS=4-7,12-15 tools/bench/echo.sh
ulimit -n 1048576; MEM_RUNS=3 tools/bench/mem.sh
taskset -c 2-5 $CARGO_TARGET_DIR/release/examples/quic-bench bulk 2048   # 以及：h3 5 64、handshakes 5 8
cargo run --release -p only-tls --example tls-bench all 1
cargo run --release -p only-crypto --example bench; cargo run --release -p only-crypto --example pk_bench
cargo run --release -p only-crypto --example gcm-sizes   # 按消息长度的 AES-GCM，对比 ring
BENCH_LEVELS=1,3,6,9 cargo run --release -p only-deflate --example bench SOURCES libc.so.6
cargo run --release -p only-deflate --example pmd_echo
cargo run --release --manifest-path tools/codec-bench/Cargo.toml
cargo run --release -p only-dpdk --example stack-bench
```

`summarize.py` 把网络脚本的 TSV 行整理成表格。`start_server` 会跳过之前运行的客户端套接字仍占用的端口
（裸机 Linux 的临时端口范围从 1024 开始）。
