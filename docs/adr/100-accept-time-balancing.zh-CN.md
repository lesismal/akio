# ADR-100：在监听器的各线程之间于 accept 时均衡连接

[English](100-accept-time-balancing.md) | 简体中文

状态：已采纳（2026-11-23）

## 背景

Linux 上的 TCP 监听器为每个 I/O 线程绑定一个 `SO_REUSEPORT` 套接字，由内核把每个新连接哈希到其中一个（ADR-001），
之后连接就留在该线程上。这个哈希只在平均意义上是均匀的。HttpArena 的 `latency-1m` 场景用 zrk 以固定的 100 万
请求/秒驱动 1024 个长连接（每个连接约 977 请求/秒），服务端 8 个 I/O 线程，约为服务端闭环能力（109 万）的 92%。
在 gpu51（Ryzen 7800X3D，服务端 cpuset 0-3,8-11）上用引擎自己的计数器（`Engine::metrics`、`LoopMetrics::open`、
读次数、循环迭代次数）和 `/proc` 中的每线程 CPU 测得：

| 发送速率 | 每线程连接数（内核哈希） | 饱和的线程 | p99 |
|---|---|---|---|
| 1.0M/s | 137 129 119 141 122 123 127 126 | 线程 3（141）：CPU 100%，每秒约 1 000 次循环迭代（其他线程约 100 000 次），读 136k/s，而被发送 138k/s | 376 ms（最大 1.2 s；榜单运行中为 1.35 s） |
| 0.9M/s | 138 132 120 133 150 137 119 95 | 线程 4（150） | 10 ms（p99.9 53 ms） |

每个连接负载相同，所以线程的负载就是它的连接数。连接最多的线程被发送的请求超过一个核能处理的量；它的积压（以及 zrk
从每个请求的计划发送时刻开始测量的延迟）在整个运行期间持续增长，而其他线程有一部分时间空闲。循环本身并无不公平：每个
就绪事件是一次 `read`、处理器、一次立即刷出。dusty-tuned（zio，在执行器之间迁移工作的多线程运行时）在同样的速率和
CPU 下 p99 为 3 ms，因为没有哪个执行器承担超过自己份额的工作。

ADR-001 不允许连接在打开后迁移；ADR-006 的 eBPF 分流按 CPU 或对端哈希放置流，而不是按负载（而读取每线程负载的 eBPF
程序需要经典 BPF 层级所没有的权限）。

## 决策

1. **连接可以在 accept 时、读取任何数据之前，被交给本监听器的另一个线程一次。** `on_open` 及之后的所有回调都在接收线程
   上运行，因此 ADR-001 仍然成立：连接终生属于一个线程，只是选哪个线程变了。
2. **规则**（`akio_core::balance`）：线程接受一个连接时，若它持有的连接比最少的线程多出 `2 + min / 32` 以上，就把连接
   交给那个线程。线程的负载是它打开的连接数加上已交给它但尚未打开的连接数（`LoopStats::load`；交接在投递前计入目标，
   因此同时 accept 的线程能看到）。每线程 128 个连接时差距被限制在约 3%；每线程连接很少时（短连接），相差 2 不会触发
   交接，因此不会每次 accept 都付出交接代价。
3. **机制**：接受连接的循环向目标循环投递 `Cmd::Adopt { stream, peer, acceptor }`（经其命令队列与唤醒，与 dial 相同），
   目标循环像自己 accept 的一样打开它。epoll/kqueue 与 io_uring 都实现了。交接的连接若到达正被 `set_threads` 退役的
   循环，会再转给一个活动循环；若到达正在关闭的循环，则被关闭（epoll），或服务完第一个请求后关闭（io_uring，与被取消的
   multishot accept 完成的连接相同）。
4. **API**：`akio::Balance { Kernel, LeastConnections }`（`#[non_exhaustive]`），通过 `Listener::balance` 设置。
   **默认是 `LeastConnections`**，因为它防止的故障（一个线程饱和而其他线程尚有余力）正出现在默认配置中，而代价很小。
   在放置是被明确要求的地方关闭：挂载了 `Accel::Ebpf` 分流程序的监听器（CPU 亲和或对端一致性哈希），以及启用了 NUMA
   `SO_INCOMING_CPU`（ADR-088）的引擎。UDP 监听器忽略它（对端由其套接字的哈希决定）。`Group::set_balance`（隐藏）
   把它传给后端。
5. **负载按连接数计**，而不是 CPU 时间：连接是线程永久继承的东西，计数精确、可从其他线程廉价读取，且在每连接负载相同
   （出故障的情形）时它就是负载。各连接代价差异很大的负载仍不会被它均衡，与之前相同。

## 影响

- 无论内核哈希如何，一个监听器的连接都分布在松弛范围之内；thread-per-core、无锁的处理器状态与每连接顺序不变。
- 在超出份额的线程上 accept 一次，代价是一次对目标的跨线程唤醒（一条命令和一次 `eventfd` 写）以及读取每个活动线程的
  计数器（roster 上的读锁）。均衡的线程只付出读计数器的代价。
- 内核选的线程不再是最终的，内核选择带来的局部性（收到 SYN 的 CPU）可能丢失；因此分流与 `incoming_cpu` 保持 `Kernel`。
- `Balance::Kernel` 完全恢复之前的行为。
- 未做：按 CPU 时间或排队请求加权；按请求均衡（那需要连接迁移，ADR-001 拒绝）。

## 测量

改动前的数据见“背景”（gpu51、HttpArena `latency-1m`、榜单运行与引擎计数器）。带此改动的同轮 A/B（`akio-lat` 对比
`akio` 与 dusty-tuned：latency-1m 的 p99 与 CPU、baseline 与 pipelined 吞吐）尚未完成：gpu51 上的 HttpArena 运行
在它开始前被暂停。`crates/akio/tests/balance.rs` 中的测试检查分布（在 macOS 上用 `Balance::Kernel` 时，4 线程的
分布测试得到 6、17、94、139 个连接）以及没有回调在其 `on_open` 线程之外运行。
