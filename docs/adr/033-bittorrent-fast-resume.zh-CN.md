# ADR-033：BitTorrent 快速续传

[English](033-bittorrent-fast-resume.md) | 简体中文

状态：已接受（2026-11-18）

## 背景

ADR-018 给 `akio-bittorrent` 客户端留下了一项未做：快速续传（fast resume）文件。重启或崩溃后
再次添加的种子，在做任何事之前都要对全部数据做哈希检查：大种子要花上几分钟的磁盘读取与
SHA-1/SHA-256 计算；来自 magnet 链接的 v2 种子还要重新发一轮哈希请求，因为从对端取得的分片层
只保存在内存里。对端、累计数据和限制也都会丢失。

续传文件要安全地回答一个问题：磁盘上哪些分片可以不读就信任？与它们一起保存的位图，只在文件自
保存后未被改动时才成立，而客户端无法看到所有改动：别的程序可能编辑文件；下载期间客户端自己也会
在保存之后继续写入，所以崩溃后文件比上次保存更新，原因却是无害的。

## 决定

1. **格式**：一个 bencode 字典，`file` = `akio-bittorrent resume`，`version` = 1，以 `checksum`
   结尾，即去掉该键后字典规范编码的 SHA-256。内容包括：主 info hash（及 v2 哈希）、名称、原始字节
   形式的 info 字典（magnet 链接重启时无需元数据交换）、已有分片位图、v2 分片层（文件根到拼接
   哈希：值得保存的默克尔状态；树由它们重建；不保存逐块哈希，因为分片是整体校验的）、每个文件一个
   `[大小, 修改时间纳秒]`（缺失或填充文件为 `[]`）、`clean` 与 `paused` 标志、至多 200 个对端
   （紧凑格式，`peers` 与 `peers6`）、tracker 与 Web 种子、跨会话的上传/下载累计与做种时间，以及
   种子的速率与做种限制（比率以千分之一计）。更高版本会被拒绝（`ResumeError::Version`）；未知键
   被忽略，所以版本 1 的读取方能接受不改变这些键含义的新增内容。
2. **解码不信任任何东西。** bencode 严格解码（深度限制、不允许尾随数据）；先检查魔数、版本和校验
   和，再检查每个字段的类型与长度（20/32 字节哈希、位图长度恰为 info 字典的分片数且多余位为零、
   分片层为整数个哈希、对端为整数个条目、每个文件一个时间戳）；info 字典的哈希必须等于 info hash；
   分片层只有与其文件根匹配才保留。属于其他种子的数据，或 info 字典与种子不同，属于 `Mismatch`。
   截断或损坏的数据绝不会 panic（模糊测试目标 `bt_resume`，它还会给变异后的字典重新封上正确的
   校验和，好让变异触及各字段），也绝不会被采用：种子会做完整检查，并报告
   `TorrentEvent::ResumeRejected`。
3. **对照磁盘校验。** `Storage::file_stamps`（新增，默认 `None`）给出每个文件的大小与修改时间；
   `FileStorage` 对其文件做 stat。时间戳与保存时不同的文件，会重新检查与它相交的所有分片（无论是否
   声称已有），只信任未改动文件中的声明——但有一个例外，使崩溃代价很小：种子运行期间做的保存
   （`clean` = 0）中仍在下载的文件（有分片缺失），无法区分客户端自己之后的写入与他人的写入，所以
   这样的文件只在消失、短于最后一个已声明分片所需长度、或长于应有长度时才重新检查。在那次保存与
   崩溃之间下载的分片会重新下载（至多一个保存间隔的量）。种子已暂停或停止、且没有已校验分片仍在
   写入时，保存是 `clean` 的；此时每个改动过的文件都会重新检查。没有时间戳的存储（内存、嵌入方
   自己的实现）在 `may_have_data()` 为真时被信任，否则丢弃。哈希检查仍在磁盘池上进行；
   `TorrentEvent::ResumeAccepted { pieces, rechecking }` 在 `Checked` 之前报告结果，
   `TorrentStats::pieces_checked` 统计读回的分片数。
4. **保存。** `ClientConfig::resume_dir`（默认无：不保存也不加载）存放
   `<主 info hash 十六进制>.resume`。维护线程在以下时机把保存任务放到磁盘池：每隔
   `ClientConfig::resume_interval`（默认 30 秒）且有记录的内容改变（分片、分片层、元数据、限制、
   状态、累计）；暂停或检查完成后不久（没有写入在进行时，最多 5 秒后）；`Client::close` 在磁盘池
   清空后保存每个种子，并记录各自在关闭前是否已暂停。检查期间从不保存（位图尚未知），在种子锁内
   取状态，之后再取文件时间戳（因此每个声明的分片都已写入），并原子写入：临时文件、`fsync`、
   `rename`，再对目录 `fsync`。`Client::remove` 删除该文件。
5. **加载。** `add_torrent` 与 `add_magnet` 使用 `AddOptions::resume_data`，否则使用种子任一
   哈希下的文件。续传数据会加入其对端、tracker 与 Web 种子；保存时已暂停的种子以暂停状态启动；
   选项未设置限制时使用其中的限制；对 magnet 链接，它带来 info 字典与分片层。`AddOptions::seed`
   仍然优先（所有分片视为已有）。
6. **API**（增量）：`client::{ResumeError, FileStamp}`、`Storage::file_stamps`、
   `ClientConfig::{resume_dir, resume_interval}`、`AddOptions::resume_data`、
   `Client::add_resume`（仅凭续传数据添加种子）、`AddError::Resume`、
   `Torrent::{resume_data, save_resume_data}`、`TorrentEvent::{ResumeAccepted, ResumeRejected}`、
   `TorrentStats::{pieces_checked, total_uploaded, total_downloaded}`。
7. **跨会话累计。** `TorrentStats::seeding_time` 现在包含续传数据中记录的做种时间，做种限制
   （ADR-018）使用跨会话累计值，所以比率或时间限制不会因重启而重置。没有续传数据时行为不变。

未做：未完成分片中的块不保存（libtorrent 的 `unfinished`）；崩溃会丢失进行中的分片，快速连接下
重新获取远不到一秒。续传数据不与其他实现的客户端互通（libtorrent 的格式在键与语义上都不同）。

## 影响

- 重启后的客户端立即做种或继续下载；崩溃至多损失最后一个保存间隔内的分片。测试
  （`tests/resume.rs`，v1、v2、混合种子各一遍）：`close` 后在没有任何对端的情况下重启且
  `pieces_checked == 0`；子进程在下载中途被 `SIGKILL`，重启后完成下载且没有任何分片被重新哈希；
  改动的文件（一个字节，大小不变）单独重新检查，其损坏分片是唯一重新下载的分片；截断、翻转、
  空的以及属于其他种子的续传文件被拒绝并做完整检查；导出与导入暂停状态、限制和 Web 种子；v2
  magnet 获取的分片层从文件和仅凭字节都能恢复。
- 开销在维护线程与磁盘池上，从不在 I/O 路径上：每个校验通过的分片多一次计数器自增。没有续传目录时完全没有
  开销。bt-bench（512 MiB、回环 TCP、gpu51、同轮 A/B 交替 5 组取中位数）：改动前 2169 MiB/s，
  改动后 2199（1.01 倍，噪声）；uTP 各组持平。
- 模糊测试：`bt_resume` 运行 661 秒（1350 万个输入），无失败。
- 对不干净保存之后写入的文件只按大小信任，意味着如果客户端在下载中途被杀时有别的程序编辑了
  文件，直到对端抱怨坏分片前都可能察觉不到；正常关闭可以弥补这一缺口。
- `MemoryStorage::new` 重启后什么都没有，所以声称其中有分片的续传数据会被丢弃（`may_have_data`
  为 false）。
